プレゼントを選ぶとき、「30代女性におすすめ30選」のような記事を読んでも決まらない。相手のことを知っているのは自分なのに、記事は相手を知らないからです。

それなら逆に、相手のことをこちらが答えて、候補を絞ってもらう形にすればいい。そう考えて **欲しいもの.com** という診断サイトを作りました。相手について 10〜16 問答えると、「もしかして、高級パジャマ？」のように贈り物の種類を当てにいきます。

この記事は、その推薦エンジンを最初のルールベースからベイズ推定に作り替えて、手書きのペルソナで測った一発的中率が **14% → 77%** （3回以内なら 96%）になるまでの話です。LLM は使っていません。

## 何を当てるのか: 商品ではなく「贈り物の種類」

最初に決めたのは、当てる対象を具体的な商品にしないことです。

```
欲求（自分では買わない贅沢）
  └ 贈り物の種類 = Concept（高級ドライヤー）
      └ 商品 = Product（ReFa / Panasonic / Dyson）
          └ 販売情報 = Offer（楽天 ¥xx,xxx）
```

診断が当てにいくのは Concept です。「高級ドライヤー」「ちょっと良い枕」「電動コーヒーミル」のような、人が贈り物として認識する粒度。商品は入れ替わるし、価格や在庫は毎日変わるので、Concept が決まってから外部 API で取りに行きます。

Concept は数百件、それぞれに 40 軸ほどの Feature（実用性、家で使う、美容、ガジェット、癒やし、お酒、料理、音楽…）を 0〜1 で持たせています。質問はこの Feature に 1 対 1 で対応します。

## v1: 一致度の平均では当たらなかった

最初の実装は素朴でした。回答から「この人はこういう人」というベクトルを作り、Concept のベクトルとの一致度で並べる。

これが当たらない。原因ははっきりしていて、

- 1 問目で 200 件が同点になる
- 「ガジェットは苦手」という強い否定が、他の軸の一致で薄まって候補が消えない
- 「甘いもの好き → はい」で、甘さと無関係なパジャマが減点される

つまり **無関係な軸を証拠として扱ってしまう** のと、 **否定が効かない** のが致命的でした。

気づくのが遅れたのは、テストの作り方が悪かったからです。最初のテストは、Concept の数値をそのまま読んで「この Concept を欲しがる人ならこう答えるはず」と機械的に回答を作っていました。ところが v1 の採点も同じ数値との近さを見ているので、これは **採点方式を採点方式で測っている** のと同じで、当たって見えて当然でした。

実際の人は、関係ない質問にも自分の性格で答えるし、「わからない」も押すし、趣味を複数持っています。そこで人物像を先に文章で書き、「この人ならこの質問にどう答えるか」を人物像から決めるペルソナで測り直したら **14%** で、誰に対しても「ペア食器」を出していました。

## v2: Concept ごとの事後確率

作り替えた v2 は、質問で当てるゲームと同じ骨格です。Concept ごとに確率を持ち、回答のたびに尤度を掛けて正規化する。

```
posterior[c] ∝ prior[c] × Π P(answer_q | c)
```

工夫はほぼ全部、尤度 `P(answer | concept, question)` の作り方にあります。

### 無関係な Concept は「母集団の基準率」で答える

「お酒を飲む？ → はい」と答えた人が、パジャマを欲しがる確率は下がるべきではありません。お酒を飲む人は人口の半分いて、その半分はパジャマも欲しがるからです。

そこで Feature ごとに `base_rate` （その性質を持つ人の割合）を持たせ、その Feature と無関係な Concept のもとでは、回答は基準率どおりに出ると見なします。

```
def baseline(base_rate):
    # その性質を持つ人の割合 r をもとに、はい/たぶん/たぶん違う/いいえ の分布を作る
    # （はい と たぶん の内訳は固定比率）
    r = clamp(base_rate)
    return {"はい": a*r, "たぶん": b*r, "たぶん違う": b*(1-r), "いいえ": a*(1-r)}
```

Concept がその Feature を強く要求するほど、基準率から「期待分布」の側へ寄せます。

```
def likelihood_row(concept, question):
    e = expectation(concept, question.feature)   # -1..1、Concept がその性質をどれだけ要求するか
    s = strength(e, question)                    # 0 なら無関係
    base = baseline(feature.base_rate)           # 無関係なときの回答分布
    kernel = KERNEL_YES if e > 0 else KERNEL_NO  # 要求する/しないときの期待分布（はい に寄る / いいえ に寄る）
    return {a: (1 - s) * base[a] + s * kernel[a] for a in ANSWERS}
```

`s = 0` の Concept は尤度比がほぼ 1 になり、その質問では動きません。これで「甘いもの好き → はい」でパジャマが減点される問題が消えました。

### 「いいえ」は「はい」より強く効かせる

Feature には 2 種類あります。

- **unipolar**: 低い値は「無関係」。美容 0.0 のパジャマは、「美容に関心がある → はい」で減点されない
- **bipolar**: 低い値は「逆の性質」。実用的 ⇔ 気分が上がるもの、家 ⇔ 外。「実用的な方が喜ぶ → はい」で飾りものは減点される

そして否定側のカーネルは正側より強い。飲まない人にお酒を出してはいけないので、「いいえ」は確実に候補を消す方向に効かせます。逆に bipolar の「逆の性質」側は正側より弱めています。家で過ごす人でもマフラーは欲しくなりうるからです。

### 「わからない」は更新しない

回答が 0（わからない）のときは尤度 1.0 を返して、事後確率をいじりません。当たり前のようで、v1 ではこれが中立値として一致度に混ざっていました。

### 事前確率

```
prior = giftability ** γ × budget_fit × gender_fit / cluster_size
```

ギフト適性は編集者が付けた値なので、質問で覆せる範囲に留めます（べき乗は調整の結果）。予算外の Concept も小さな下限を残して完全には消しません。全滅を防ぐためです。

`cluster_size` で割っているのは、質問では分けられない Concept 群（食器 6 種類など）を 1 つの仮説として数えるためです。割らないと、6 件の食器クラスタが合算で 6 倍の事前確率を持ち、序盤の 1 位を独占しました。提示はクラスタの代表で行い、商品はメンバーそれぞれの検索語で集めます。

## 質問選択: 期待情報利得、ただし序盤は「領域」から

次に出す質問は、未回答の Feature に対応する質問ごとに、事後確率のエントロピーがどれだけ下がるかの期待値を計算して、最大のものを選びます。上位の確率質量に入る Concept だけで計算すると十分速いです。

```
for question in candidates:
    rows = [likelihood_row(c, question) for c in focused_concepts]
    expected_after = 0
    for a in ANSWERS:
        joint = [p * row[a] for p, row in zip(probs, rows)]
        p_a = sum(joint)
        conditional = [j / p_a for j in joint]
        expected_after += p_a * entropy(conditional)
    gain = entropy(probs) - expected_after
```

ただし、これだけに任せると失敗しました。弱い証拠で浮いた暫定 1 位の周辺を確かめる質問に序盤の枠を使ってしまい、その人の本当の領域（釣り、お酒）を聞かないまま終わるのです。

なので **序盤の数問は「領域」の軸（家か外か、実用か、食、美容、ガジェット、おしゃれ、趣味、癒やし、お酒、運動、体験）からだけ選ぶ** ようにしました。人がプレゼントを選ぶときも、まず人となりを掴んでから細部を詰めます。この段階を長くしすぎると逆に精度が落ちました。細部を聞く枠が無くなるからです。

## 二択と、理由つきの「違う」

質問だけでは分けられない局面で、「A と B ならどっち？」という二択を出します。1 位と、それに似ていない上位候補を並べ、二択の期待利得が最良の質問を上回るときだけ使います。「どちらも違う」は両方を下げます。

提示に対する「違う」には理由を選べるようにしました。理由で次の探し方が変わります。

![提示画面。「これだ！」「惜しい」「違う」と、効いた軸のタグ](https://static.zenn.studio/user-upload/deployed-images/008dd9891934f5013abcff0a.png?sha=c086430d0c3c185fb7536a62d21983b5affcc5e9)  
*提示のときは、効いている軸を「家で使うもの・寝室まわり・身につけるもの、だから」と添える。内部の feature 名は出さない。*

| 理由 | エンジンの動き |
| --- | --- |
| 持ってる | 同じ系統の近い Concept を上げる（方向は合っている） |
| 高すぎる | 予算の上限を下げて探し直す |
| 趣味じゃない | その方向の近傍をまとめて下げる |
| とにかく違う | 近いものも下げる |

「違う」の後の当たりが目に見えて増えました。

## 停止条件と「絞られている感」

1 位の確率が一定を超えるか、1 位と張り合える候補（1 位に対して一定以上の確率を持つもの）が無くなったら提示します。届かなければ上限の問数で提示。1 問あたりの証拠を意図的に弱くしている（人は複数の領域を持つ）ので、たいてい上限で止まります。

画面の進捗バーは質問数ではなく、この「張り合える候補の数」を対数で見せています。候補の総数は出しません。数字を見せると母数の印象に引っ張られるので、バーだけです。

## 評価: ペルソナを手で書く

合成ユーザーで測ると判断を誤ったので、評価は **手書きのペルソナ** に切り替えました。「40代の夫、毎朝コーヒーを淹れる、家で過ごすのが好き、ガジェットは面倒がる」のような人物像を先に書き、その人なら各質問にどう答えるかを人物像から決めます。当たりは 1 つに決めず複数許します。

20 数人のペルソナで、現在の結果は次のとおりです。

|  | 一発的中 | 3 回以内に的中 |
| --- | --- | --- |
| v1（一致度の平均） | 14% | 36% |
| v2（ベイズ + 情報利得） | 77% | 96% |
| v2、回答にノイズを乗せた場合 | 72% | 91% |

外れ方も見えるようになりました。揺れなしで外しているのは「毎朝コーヒーを淹れる夫」で、家・食・手間の回答から低温調理器、鉄フライパンと調理道具に寄ります。コーヒー器具と調理器具を分ける軸が無いからです。人が複数の強い領域を持つとき、聞かなかった領域は当てられない。ここは質問を増やすより、最初に「相手が好きなもの」を複数選択で聞く方が効きそうで、次の課題です。

ペルソナはテストにもしていて、精度が一定を下回ると CI が落ちます。推薦ロジックやマスタを触ったら、数字だけでなく transcript を読むようにしています。「その質問いる？」は数字では掴めません。

## キャラクターはエンジンの状態表示

占い師の猫「ミィ」が診断中ずっと画面にいますが、これは飾りではなくエンジンの状態表示です。表情とセリフは、1 位の確率、エントロピーの変化量、直前の反応から決めています。乱数では決めません。

| 状態 | 条件 |
| --- | --- |
| 迷っている | 確信度が低い |
| 大きく絞れた | 直前の回答でエントロピーが大きく下がった |
| 見えてきた | 確信度が提示に近づいた |
| 外した | 提示に「違う」 |

エンジンは数字だけを返し、UI 側で表情に変換します。将来モデルを差し替えても UI は変えなくて済みます。

## 構成

- 推薦エンジン: Python。Concept / Feature / Question は YAML
- API: FastAPI、フロント: Next.js、どちらも Cloud Run
- DB: Cloud SQL (PostgreSQL)。診断の進行は journal に追記し、リクエストごとに再生して状態を復元します。エンジンが決定的なのでメモリに状態を持たなくてよく、複数インスタンスで動きます
- 商品: 楽天の商品検索 API。価格・在庫は保存せず、短期キャッシュのみ

楽天 API まわりで踏んだこと。

- サーバーから叩くと `Origin` ヘッダが無くて 403 になる（2026 年 2 月の仕様変更）。登録サイトの URL から組み立てて送る
- 検索結果に中古品が大量に混ざる。 `NGKeyword` で「中古 訳あり ジャンク」などを除外
- 申告 QPS ではなく、実際に通る間隔に合わせないと 429 が返る

## LLM を使わなかった理由

候補生成や Feature の初期タグ付けには使いましたが、推薦の本体には入れていません。理由は 2 つです。

1. 「なぜこの質問を出したか」「なぜこれを当てにいったか」が説明できないと、外したときに直せない
2. 蓄積したいのは「誰に何を贈ると刺さるか」の構造化データで、それは推薦が構造化されていないと貯まらない

診断で「これだ！」と押された、または買いに行った Concept を、相手・年代・予算ごとに集計してランキングにする予定です。100 診断集まった条件から公開します。

## 最後に

診断は無料・登録なしで、相手のことを答えるだけです。よければ試してみてください。当たったら「これだ！」を押してもらえると、次に同じ条件で悩む人のデータになります。
