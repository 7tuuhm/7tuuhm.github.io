## なぜ「本番運用」は別物なのか

[

はんぺん

2026.09.14に更新

](https://zenn.dev/hampen2929)

Claude Codeと対話しながら、差分からコミットメッセージを作らせたり、失敗したテストを直させたりして、ちゃんと動いた。 `claude -p` も一度は試したかもしれない。次はこれをCIに入れて、毎晩自動で回したい——本書を開いたあなたは、おそらくそのあたりにいるはずです。

そこで最初の章では、本書全体を貫く問いをひとつ置きます。

**対話で問題なく使えているものを、そのまま無人にしてはいけないのはなぜか。**

「そのまま」ではダメな理由を4つの壁として整理し、それぞれの壁に本書のどの章が答えるかという地図を描くのが本章の仕事です。手はまだ動かしません。しかし、この地図がないまま後の章のコマンドやYAMLを写経しても自分のケースに応用が利かないので、先にここを固めます。読み終えたら、自分のリポジトリで最初に無人化するタスクを1つ選べる状態を目指します。

## 筆者の環境で起きた、対照的な2つの出来事

抽象論に入る前に、実際にあった話を2つします。

1つめ。筆者は、個人開発しているWebサービスの定型運用——毎晩のコンテンツ更新や週次の定型処理——を、AIエージェントの定期実行に任せています。人間は結果をたまに眺めるだけで、これは静かに回り続けています。

2つめ。同じ筆者の手元で、Claude Codeが作業ディレクトリの外にある `~/.ssh/config` を上書きしたことがあります。頼んでいたのはリポジトリ内で完結するはずの作業で、SSHの設定は何の関係もありません。このときは気づいて対処できましたが、これが夜中の無人ジョブで起きていたら、翌朝サーバにつながらない理由を誰も知らないところから一日が始まっていたはずです。

同じ人間が、同じようにAIエージェントを使って、片方は無人で回し続け、もう片方では事故を起こしている。この差はモデルの賢さの差ではありません。 **設計の差** です。前者には、成果物が出ていく通り道が決まっていて、その途中に機械の検証があり、実行時間や費用に上限がありました。後者は「対話で使う前提の環境」のまま、任せる範囲だけが広がっていました。

本書で扱う「本番運用」とは、この設計のことです。通り道・検証・上限という3つの言葉は、以降の章で具体的な設定に置き換わっていきます。

## あなたが「ついで」にやっている5つの仕事

対話利用がうまく回っているとき、実はモデルの隣で人間が5つの仕事を同時にこなしています。あまりに自然にやっているので、仕事だと意識すらしていないはずです。

1. **ブレーキ** — 危険な操作の確認ダイアログに、内容を見てy/nを返す。おかしな方向に走り出したら止める
2. **品質検査** — 出力を目で見て「動きはするけど、これは違う」に気づき、その場で直させる
3. **承認** — 結果を確認してからコミットする。つまり、すべての変更に人間の承認が挟まっている
4. **経理** — 「今日はけっこう使ったな」と、体感でコストを把握している
5. **説明責任** — 何をやらせて何が起きたか、聞かれればあなたが説明できる

ヘッドレス実行に切り替えた瞬間、この5人の働き者が全員いなくなります。 `-p` フラグは対話UIを外すだけのフラグではなく、 **人間が無意識に担っていたガードレール・品質保証・承認フロー・コスト管理・監査対応を、まとめて外す** フラグでもあるのです。

無人運用の設計とは、この5つの仕事を仕組みに移植することです。

![対話利用で人間が担っている5つの仕事を、無人運用では仕組みに移植する](https://static.zenn.studio/user-upload/deployed-images/027277193715c40300c4e674.jpg?sha=ffc1ef5b5d031c5d62f464b8c2a3aa82f188b215)

そう捉えると、本書の構成はほぼ自動的に決まります。5つの仕事のそれぞれを、何で置き換え、どの章で作るかを対応させたのが次の表です。

| 対話であなたがやっていた仕事 | 無人運用での置き換え | 対応する章 |
| --- | --- | --- |
| ブレーキ | 権限の事前設計・Hooks・機械的上限 | ガードレール / セキュリティ |
| 品質検査 | テスト・ビルドを合格条件にする検証ゲート | 自律修正ループ / 品質評価 |
| 承認 | 出口をPRに限定し、人間のマージを最後の砦にする | 自律修正ループ / 企業環境への導入 |
| 経理 | ジョブ単位の計測・上限・1修正あたりコスト | コスト管理 |
| 説明責任 | ログ・実行の追跡可能性・承認の記録 | セキュリティ / 企業環境への導入 |

この移植をやらずに「対話の環境のままフラグだけ変える」とどうなるか。それが4つの壁です。

## 4つの壁

## 壁1: 暴走 — 止める人がいない

対話モードのClaude Codeは、危険な操作の前に確認を求めてきます。無人実行では誰も「y」を押せません。だから、 **事前に許可した範囲のことしか起きないように設計する** 必要があります。ここまでは分かりやすい話です。

やっかいなのは、暴走が「派手な破壊」の形を取るとは限らないことです。実際に観測される暴走は、もっと地味です。

- 修正対象と関係ないファイルまで「ついでに」直す（善意のスコープ逸脱）
- テストを通すために、テストの期待値のほうを書き換える
- 失敗→リトライ→失敗のループで、一晩中APIを叩き続ける
- 作業ディレクトリの外への書き込み（先ほどの `~/.ssh/config` はこれ）

どれも、1回の対話なら笑って直せるレベルです。しかし無人ジョブは毎晩走り、失敗しても誰も見ていません。対話利用での「たまに起きる小さな逸脱」は、無人運用では「いつか必ず起きる事故」に変わります。

対策の骨子は、 **エージェントの善意や賢さに頼らず、機械的な境界で囲う** ことです。ツール権限の最小化、書き込み先のスコープ制限、Hooksによる決定的なチェックポイント、差分サイズ・ターン数・コストの上限。「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」の章で設計します。

## 壁2: 品質 — 「動いた」と「正しい」の間

LLMの出力は非決定的です。同じプロンプトでも、毎回微妙に違うものが返ります。対話利用では、このばらつきをあなたの目が吸収していました。10回に1回おかしな出力が来ても、「違う、そうじゃない」と言い直せば済むからです。

無人運用では、このばらつきが **確率の問題** に変わります。10回に1回の品質問題は、毎晩実行すれば10日に1回、10リポジトリに展開すれば毎晩どこかで起きる計算です。そして対話と違い、おかしな出力に気づく目がその場にありません。

さらに、「テストが通った」は「意図どおり」を意味しません。壁1で挙げた「テストの期待値を書き換えて通す」は極端な例ですが、もっと平凡なケース——動くが設計方針に反する実装、報告文には正しいことが書いてあるのに差分は別のことをしている——のほうが数は多いです。

対策は、 **合格条件を人間の目から機械検証（テスト・ビルド・lint・型チェック）に移し、機械で判定できないものを人間のレビューに正しく残す** こと。どこまでを機械に任せ、何を人間に残すかの線引きが設計の本体です。「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で検証ゲートの基本形を、「 [品質評価](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/quality-evals) 」の章で受理率・手戻り率といった運用メトリクスを扱います。

## 壁3: コスト — 対話の感覚が通用しない

対話利用のコスト感覚は「今日はたくさん使ったな」程度で、それで実害はありません。使うのはあなた1人で、使った分の成果も体感できているからです。

無人運用では、この感覚が3つの理由で壊れます。

第一に、 **掛け算になる** 。毎晩×対象リポジトリ数×ジョブ種別で、1回数十円のジョブが月数万円になります。第二に、 **失敗にも全額かかる** 。人間なら途中で見切りをつけますが、無人ジョブは最後まで走ってから失敗します。リトライ設計を誤ると、失敗ジョブほど高くつきます。第三に、 **成果と紐づかない** 。「先月AIに5万円使った」だけでは、それが安いのか高いのか、誰にも判断できません。

対策は、計測をジョブ単位で仕込み（ `--output-format json` の出力にはコストのフィールドがあります）、ジョブごとに上限を掛け、 **「1修正あたりいくら」という単位でROIを語れる状態** を作ることです。これは技術の話であると同時に、稟議の話でもあります。「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」の章で扱います。

## 壁4: 監査 — 「誰の意思か」に答えられるか

最後の壁は、個人で使っている限りは見えません。チーム、そして会社に持ち込んだ瞬間に現れます。

- このコミットは誰の意思で入ったのか。AIが書いたなら、責任は誰が持つのか
- 本番で事故が起きたとき、AIジョブが何を読み、何を実行し、なぜその変更をしたのかを遡れるか
- セキュリティチームに「このエージェントは何ができて、何ができないのか」を説明できるか

筆者は本業で規制の強い業界のシステム開発に関わっていますが、この種の環境でAI導入の話をすると、最初に聞かれるのは性能でもコストでもなく監査可能性です。逆に言えば、ここに答えを持っている人が、チームでいちばん強い。

この対策は後付けできません。 **実行のログが残る構造、変更が必ずPRを通る構造、人間の承認が記録される構造** を、最初から選ぶことです。「 [セキュリティ](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/security) 」の章の監査ログと、「 [企業環境への導入](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/enterprise) 」の章の承認フロー設計で扱います。

## 「守り」は2種類ある — 事故と攻撃

4つの壁のうち「暴走」には、性質の違う2つの顔があります。本書はこれを分けて扱うので、早めに用語を導入しておきます。

**事故（Safety）** は、誰にも操られていないのに間違えることです。スコープ外のファイルを触る、やりすぎる、無限ループに入る。確率的で、悪意はありません。

**攻撃（Security）** は、外部の入力がエージェントを操ることです。ここで思い出してほしいのは、エージェントが読むものはすべて「入力」だという事実です。リポジトリのコード、コミットメッセージ、Issue本文、依存パッケージのドキュメント——CIで動くエージェントは、これらを「指示かもしれないもの」として読んでしまう性質を構造的に持っています。悪意ある文字列を仕込んだIssueが、書き込み権限を持つエージェントに届いたら何が起きるか。

本書では、CIの中のエージェントを「 **書き込み権限を持つ、操られ得る従業員** 」としてモデル化します。善意だが騙されやすい新人に、リポジトリへの書き込み権限とシークレットへのアクセスを渡している——この見立てに立つと、権限の絞り方も、ログの取り方も、自然に決まっていきます。

事故と攻撃は、対策の道具立てが違います。事故には上限とチェックポイント、攻撃には信頼境界と権限設計。第2部で1章ずつ使って設計します。

## リファレンスアーキテクチャ — 本書が組み立てるもの

4つの壁に同時に答えるために、本書は1つのリファレンスアーキテクチャを軸に進みます。全体像を先に見せます。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__376bc0a04f583" frameborder="0"></iframe>

線のつなぎ方に、本書の主張がすべて入っています。図で見てほしいのは2点です。 `claude -p` の箱から出た実線は、検証ゲートを通らずに成果物へ届く経路を持たないこと。そして、実行・検証・承認のそれぞれから点線が記録へ向かっていることです。この2つを言葉にすると、次の4つの原則になります。

1. **出口は必ずPull Request。** エージェントはmainに直接書き込みません。どれだけ検証を厚くしても、本番に入る変更の最終承認は人間のマージ操作として残します。これが品質の最後の砦であり、監査の壁への答えの半分です
2. **検証は機械が先、人間が後。** テスト・ビルド・lint・型チェックが先に走り、人間は機械が通したものだけを見ます。人間のレビューを「全部見る」仕事から「機械に判定できないところを見る」仕事に再定義します
3. **権限と上限は実行の外側で決める。** プロンプトで「気をつけてね」とお願いするのではなく、権限・スコープ・上限をCIの設定として宣言します。エージェントがどう振る舞おうと越えられない線を、エージェントの外に引きます
4. **すべての段が痕跡を残す。** 何を実行し、いくら使い、誰が承認したか。運用のメトリクス（受理率・コスト）も監査対応も、この記録の上に立ちます

見てのとおり、この図の構成要素は本書の章立てそのものです。トリガーと実行の設計が第1部、実行を囲う権限・上限と信頼境界が第2部、検証ゲートと記録の活用が第3部。そして最終章で、この図の全体を、架空のタスク管理アプリを題材にした1つのサンプルリポジトリとして動かします。この題材はシリーズ共通で、続刊でも同じリポジトリを育てていきます。

## 無人化に向くタスク、まだ向かないタスク

地図の最後に、「何から無人にするか」の判断基準を置きます。壁を越える設計を持っていても、最初のタスク選びを誤ると、信頼を積む前に事故で終わるからです。

判定は3つの問いでできます。

1. **失敗は可逆か。** 失敗してもPRが1本無駄になるだけか。それとも取り返しがつかないか（本番DBのマイグレーション、外部への通知送信）
2. **合否を機械判定できるか。** テスト・ビルド・lint・スキーマ検証で「できた」を判定できるか。それとも人間の判断がないと良し悪しが決まらないか
3. **文脈は閉じているか。** リポジトリの中の情報で完結するか。それとも暗黙の仕様・組織の事情・口頭合意を知らないと正解が出ないか

3つすべてYESが、最初の候補です。具体的にはこうなります。

| 向いている（3つYES） | 条件付き | まだ向かない |
| --- | --- | --- |
| lint指摘の修正 | 障害の一次調査（読み取り専用なら安全） | 仕様が曖昧な新機能の実装 |
| 型エラーの解消 | 依存ライブラリの更新（テストの厚み次第） | 不可逆な操作を含む作業 |
| テストの追加・ドキュメント同期 | リファクタリング（検証の厚み次第） | UX・仕様の判断を含む変更 |
| PRの一次レビュー・定型レポート |  |  |

本書の題材であるタスク管理アプリで、この3つの問いを当ててみます。仮に、タスクの期限を扱う関数に型エラーが出たとします。直し方を誤ってもPRが1本落ちるだけで可逆です。型エラーが消えたかは `tsc` が判定し、周辺を壊していないかは既存のテストで見ます。型が合っただけでは直し方が妥当だとまでは言えないので、PRのレビューは残りますが、機械で判定できる部分がはっきりしています。必要な情報は該当ファイルと型定義に閉じています。3つともYESなので、これが本書で最初に無人化する題材になります。

同じアプリの、期限切れタスクをユーザーへ通知する処理ではどうでしょうか。ここは2つに分けて考えます。通知処理のコードを直してPRにする仕事は、コードの変更自体は可逆です。ただし、誰にいつ送るべきかという判断はリポジトリの外にあり、 `tsc` とテストが通っても仕様として正しいかは人間が検収するしかありません。問い2と問い3が弱くなり、表の中央から右へ寄ります。一方、通知を実際に送る操作そのものをジョブに任せるのは別の話です。送ってしまった通知は取り消せないので、問い1がNOになり、表の右列に落ちます。表を覚えるより、この3問を自分のタスクに当てる練習のほうが役に立ちます。

もうひとつ、順序の原則があります。 **読み取り専用のジョブから始める** ことです。調査レポート、PRの一次レビュー、コード分析——書き込み権限のないジョブは事故の被害半径が小さく、運用の勘所（コスト感、出力のばらつき、ログの見方）を安全に学べます。書き込みを伴う自律修正は、その次です。信頼は一段ずつ積む。この階段は、本書全体で繰り返し出てきます。

## まとめ

- 対話利用が回っていたのは、人間が **ブレーキ・品質検査・承認・経理・説明責任** の5つの仕事を無意識にやっていたから。無人運用とは、この5つを仕組みに移植すること
- 移植を怠ると4つの壁に当たる。 **暴走** （止める人がいない）、 **品質** （ばらつきを吸収する目がない）、 **コスト** （掛け算で膨らみ、成果と紐づかない）、 **監査** （誰の意思か答えられない）
- 守りは **事故（Safety）と攻撃（Security）** に分けて設計する。CIの中のエージェントは「書き込み権限を持つ、操られ得る従業員」
- アーキテクチャの背骨は4つ。 **出口はPR / 検証は機械が先 / 権限と上限は外側 / すべてが痕跡を残す**
- 最初の無人化は「失敗が可逆・合否が機械判定できる・文脈が閉じている」タスクから。できれば読み取り専用から

次の「 [ヘッドレス実行の基礎](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/headless-basics) 」の章から手を動かします。この章で決めた「読み取り専用から」「出口はPR」「上限は外側」を前提に、無人運用の最小部品である `claude -p` を分解し、JSON出力・認証・タイムアウトとリトライまで、CIに載る形へ組み上げていきます。
