## ガードレール — 事故を防ぐ

[

はんぺん

2026.09.14に更新

](https://zenn.dev/hampen2929)

第2部は守りの話です。「 [なぜ「本番運用」は別物なのか](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/why-production-is-different) 」の章で、守りは事故（Safety）と攻撃（Security）に分かれると書きました。この章は前者——誰にも操られていないのに間違える、確率的な事故——を仕組みで防ぎます。

ここまでのジョブで、事故を止めているのはプロンプトの禁止事項と、実行後の差分検査でした。この章を読み終えると、その2つの間に「実行前に判定する層」と「OSが強制する層」を足し、どの層が何を止め、何を止められないかを説明できるようになります。

まず、予告していた実話からです。

## あの日、何が起きたか

筆者がClaude Codeに頼んでいたのは、ドキュメントの作成でした。リポジトリの中で完結する、SSHとは何の関係もない作業です。

事故に気づいたのは、そのセッション中ですらありません。 **サーバーにSSHできなくなった** ときです。調べると、 `~/.ssh/config` ——ホスト名や鍵の場所を書いておくSSHの設定ファイル——が上書きされていました。作業ディレクトリの外、ホームディレクトリ直下の、頼んだ作業と無関係なファイルです。

幸い、ローカルに設定のバックアップがあり、復旧は30分ほどで済みました。しかしこの事故は、30分の作業ロスよりずっと重い教訓を3つ残しました。

**第一に、事故は「関係ない作業」から来ます。** 危険なタスクを頼んだから危険な事故が起きる、という比例関係を無意識に想定しがちですが、実際はドキュメント作成という無害きわまりない依頼からSSH設定が壊れました。エージェントは確率的に動きます。「このタスクなら安全」というタスク単位の見積もりは、防御としては機能しません。

**第二に、発生と発覚が分離します。** 上書きの瞬間には何も起きません。症状が出るのは、次にSSHを使おうとしたとき——数時間後かもしれないし、数日後かもしれない。対話モードで人間が隣にいてもこれです。無人ジョブなら、発覚はさらに遅れ、「なぜ壊れたか」を遡る材料も残っていなかったでしょう。

**第三に、最後に助けてくれたのは、防御ではなく備えでした。** 事故を防いだものは何もありません。被害を30分に抑えたのはバックアップ、つまり「戻せる」仕組みです。守りは1枚の壁ではなく、防ぐ・止める・気づく・戻せるの層で考える必要があります。

筆者はこの事故のあと、「書き込みは作業ディレクトリ内に限定する」というルールを作りました。しかし、指示やルールを書き足すだけでは同じ穴が残ることも、もう分かっていたはずです。エージェントへの指示は「お願い」であり、お願いは確率的に破られる——「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で書いたとおりです。この章は、あのルールを **実行時に検査する仕組み** に落とす章です。

## 原則 — ルールはモデルではなくハーネスに書く

道具に入る前に、この章全体を貫く原則をひとつ。

公式ドキュメントに、本書の守りの設計思想をそのまま要約した一文があります。いわく、権限ルールを強制するのはClaude Code（実行環境）であって、モデルではない。プロンプトやCLAUDE.mdの指示が変えられるのは、エージェントが **何を試みるか** まで。 **何が許されるか** は、実行環境側の設定だけが決めます。

つまり守りには階段があります。

1. **お願い** （プロンプト・CLAUDE.md）— 意図を伝える。確率的に破られる
2. **宣言** （permissions設定）— 実行環境が判定する。モデルの気分と無関係
3. **追加の強制** （OSサンドボックス・Hooks）— 対象プロセスや対象イベントの操作を止める。適用外の経路は別に塞ぐ

「自律修正ループの設計」の章で「プロンプトで意図を伝え、機械で強制する」と書いた二層防御を、この章で3段の階段として完成させます。以降のレシピはすべて、お願いをひとつずつ宣言と強制に昇格させる作業です。

図でpermissionsから下が2本に分かれているのは、HooksとOSサンドボックスが並列の層で、上下関係ではないからです。Hooksはツール呼び出しという単位で、サンドボックスはプロセスという単位で止めます。どちらも通り抜けた先に、最後の「備える」層があります。以下、この図を上から順に組み立てます。

## 第1層: permissions — 宣言的な境界

最初の層は `settings.json` の `permissions` です。allow / deny / ask の3種類のルールを書きます。評価順序は重要なので正確に押さえてください。 **deny → ask → allow の順に評価され、最初にマッチしたルールで決まります。** 広いdenyは狭いallowに勝つため、「原則禁止・一部例外」というdenyの例外は作れません。denyは本当に恒久的に塞ぎたいものだけに使います。

あの事故に効いたはずの宣言を書いてみます。3行目の `Edit(~/.ssh/**)` がそれで、残りは同じ考え方で「エージェントの仕事に絶対に含まれない場所」を並べたものです。

```
{
  "permissions": {
    "deny": [
      "Edit(.git/**)",
      "Edit(.claude/**)",
      "Edit(~/.ssh/**)",
      "Edit(~/.aws/**)",
      "Edit(~/.config/**)",
      "Read(~/.ssh/id_*)",
      "Read(.env*)",
      "Read(**/*.pem)",
      "Bash(git push *)"
    ]
  }
}
```

ファイルパスのルールはgitignore構文で、アンカーの書き分けが4種類あります。ここを雑に書くと「効いているつもりのdeny」ができるので、表で押さえます。

| 書き方 | 基準点 | 例 |
| --- | --- | --- |
| `//path` | ファイルシステムのルート | `Read(//etc/**)` |
| `~/path` | ホームディレクトリ | `Edit(~/.ssh/**)` |
| `/path` | 設定ファイルの置き場所 | プロジェクト設定の `Edit(/src/**)` = `<プロジェクト>/src/` |
| `path` `./path` | カレントディレクトリ | `Read(.env*)` |

このdenyのセットは `.claude/settings.json` に置いてリポジトリにコミットします。「Claude Code入門を終えた人が、次にやるべき5つのこと」で権限設定をチーム資産にする話をしましたが、無人運用ではさらに意味が増します。CIで動くジョブが `--settings` でこのファイルを読み込めば、 **対話とCIで同じ境界** が効きます。ただし `--bare` は設定を自動で読まないので、「 [ヘッドレス実行の基礎](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/headless-basics) 」の章のとおり明示的に渡す必要があります。裏返すと、「ヘッドレス実行の基礎」と「自律修正ループの設計」の最小例には `--settings` がなく、このファイルをコミットしただけではCIのジョブには何も効いていません。「サブエージェント編成」の実例では先に足してあります。

知っておくべき仕様の機微が2つあります。

もうひとつは適用範囲です。Read/Editのdenyルールは、専用ツールだけでなく、 **Bash内の既知のファイルコマンド（ `cat` や `sed` など）にも適用されます** 。ただし万能ではありません。エージェントが書いたNodeスクリプトがファイルを開く、といった **任意のサブプロセス経由のアクセスには効きません** 。宣言の層はここまで。その穴を塞ぐのが次の層です。

## 第2層: サンドボックス — OSが強制する境界

permissionsは「Claude Codeが判定する」層でした。その判定ごと迂回されるケース——サブプロセス経由のアクセス、そして後の章で扱うプロンプトインジェクションでモデルの判断自体が乗っ取られるケース——に備えるのが、OSレベルのサンドボックスです。

Claude Codeにはサンドボックス機能が組み込まれています。macOSではOS標準のSeatbelt、LinuxとWSL2では追加パッケージを使い、 **Bashコマンドとそのすべての子プロセス** に対して、触れるファイルシステムの範囲と接続できるネットワーク先をOSが強制します。設定した境界の外は、エージェントがどう判断しようと、どんなスクリプトを経由しようと、OSが拒否します。

- ファイルシステムの境界は、サンドボックス設定とRead/Editのdenyルールがマージされて決まります。第1層で書いた宣言が、そのままOS強制の材料になります
- ネットワークは許可ドメイン・拒否ドメインのリストで制御します。「どこにでも接続できる」を潰しておくことは、「セキュリティ」の章で扱うデータ持ち出し対策の土台になります
- 対話セッションでは `/sandbox` コマンドで状態確認と設定ができます

サンドボックスを有効にすることと、境界内のコマンドを自動承認することは別の設定です。有効化しただけなら承認の流れは通常のpermissionsのままで、サンドボックス内のBashを確認なしで通すのは自動許可のモードに切り替えたときだけです。そのモードでも、明示的なdeny・askルールやplanモードなどの条件は残るので、「全コマンド確認不要」にはなりません。この区別を押さえたうえで言えば、この層は安全性と同時に **自律性を上げる** 装置でもあります。1コマンドずつ人間が承認する運用より、「境界を設計して、中では自由にやらせる」運用のほうが、無人化には素直につながります。

CIの文脈ではもうひとつ外側の層があります。GitHub Actionsのランナー自体が使い捨ての仮想マシンであることです。ただし「ランナーは使い捨てだから安全」と考えるのは早計で、ランナーの中にはシークレットとトークンがあります。この話は「セキュリティ」の章で正面から扱います。

## 第3層: Hooks — 自作の強制チェックポイント

宣言で書き切れない条件は、Hooksでコードにします。Hooksはツール実行の前後などのタイミングで任意のコマンドを実行できる仕組みで、ここでは **PreToolUse** ——ツール実行の直前に走り、実行を止められるフック——だけに絞ります。

フックはstdinでイベント情報（JSON）を受け取ります。ツール名は `tool_name` 、編集対象のパスやコマンドは `tool_input` に入っています。ブロックする方法は2つあり、シンプルにexit code 2で止めるか、JSONで `permissionDecision: "deny"` と理由を返すかです。以下の例では、判定処理自体の異常も拒否にするため、exit code 2とstderrの理由を使います。

あの事故の再発防止を、そのままコードにしてみます。 **書き込み系ツールの対象パスが、プロジェクトディレクトリの外なら拒否する** フックです。読むときの中心は `resolve()` と `is_relative_to()` の2行です。前者で相対パスとシンボリックリンクを実体のパスに直し、後者でプロジェクト直下に収まるかを判定します。文字列の先頭一致ではこの2つを兼ねられません。

```
#!/usr/bin/env bash
# 判定処理の異常もexit 2に変換し、ツールを止める。
python3 -c '
import json, os, sys
from pathlib import Path
try:
    event = json.load(sys.stdin)
    root = Path(os.environ["CLAUDE_PROJECT_DIR"]).resolve(strict=True)
    name = event["tool_input"]["file_path"]
    if not isinstance(name, str) or not name:
        raise ValueError("file_path is missing")
    target = Path(name)
    if not target.is_absolute():
        target = Path(event["cwd"]) / target
    target = target.resolve()  # 既存の親と対象のシンボリックリンクも解決
    if target == root or not target.is_relative_to(root):
        raise ValueError("outside project")
    if target.relative_to(root).parts[0] in {".git", ".claude"}:
        raise ValueError("protected configuration")
except Exception:
    print("書き込み先がプロジェクト内と確認できないため拒否", file=sys.stderr)
    sys.exit(2)
' || exit 2
```

Python 3.9以降を使い、 `chmod +x .claude/hooks/block-outside-writes.sh` で実行可能にします。`.git/` と `.claude/` はプロジェクト内でも拒否します。存在しない新規ディレクトリも判定できますが、判定後にリンク先が変わる競合までは防ぎません。

```
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-outside-writes.sh"
          }
        ]
      }
    ]
  }
}
```

このフックは **Edit / Writeツール経由の書き込み** を拒否します。BashやMCPなど別経路は対象外です。 `--bare` では前述の `--settings .claude/settings.json` を明示しないと登録されません。フック本体と設定をエージェントが変更できない場所で管理し、別経路を塞ぐツール制限やOSサンドボックスと組み合わせて使います。

同じ型で、危険コマンドのパターン拒否も書けます。 `matcher` を `Bash` にして、 `tool_input.command` を検査し、 `rm -rf` の広範囲指定や `curl | sh` のようなパターンを弾く——構造は上と同じなので省略します。

Hooksを使ううえでの規律を2つだけ。 **第一に、宣言で書けるものは宣言で書く。** `Bash(git push *)` ならpushの基本形を1行で拒否できます。ただし、 `git -C` など表記の違いをこの1行で網羅できるとは考えず、本書の修正例ではBash自体を提供しません。フックはパスの正規化や複合条件など、表現力が必要なときの道具です。設定より自作コードのほうが壊れやすいからです。 **第二に、フックも壊れる前提でいる。** フックスクリプトのバグは防御の穴です。だからこの章は層を重ねています。フックが死んでも、permissionsとサンドボックスは生きています。

## 第4層: 機械的上限 — 被害半径を設計する

「ヘッドレス実行の基礎」の章で、時間・ターン・コストの3系統の上限を導入しました。あのときは「ハングや高額ジョブを止める安全弁」として入れました。ガードレールの文脈でこれを見直すと、上限の役割がもうひとつ見えてきます。 **上限は異常の検出器です。**

上限は「成功を邪魔しない範囲で、できるだけ低く」設定します。正常なジョブの実測の2〜3倍が目安です。正常時に当たらない水準に置いた上限に当たったということは、それ自体が「いつもと違う何かが起きている」というシグナルであり、ジョブを止めて人間に知らせる正当な理由になります。上限到達を「失敗」ではなく「エスカレーション」として扱う——「自律修正ループの設計」の章の出口設計に、そのままつながります。

この文脈で、4つめの上限を足します。 **変更量の上限** です。

```
# 検証ステップに追加: 差分の行数とファイル数に上限を掛ける
# 前章の範囲検査で新規ファイルを拒否した後に使う。
# HEADとの差分ならステージ済みの変更も含む。
changed_files=$(git diff --name-only HEAD | wc -l)
if git diff --numstat HEAD | awk '$1 == "-" || $2 == "-" {found=1} END {exit !found}'; then
  echo "::error::行数を数えられないバイナリ差分は対象外"
  exit 1
fi
changed_lines=$(git diff --numstat HEAD | awk '{s+=$1+$2} END {print s+0}')
if [ "$changed_files" -gt 10 ] || [ "$changed_lines" -gt 300 ]; then
  echo "::error::変更量が上限を超過（${changed_files}ファイル/${changed_lines}行）。破棄する"
  exit 1  # 使い捨てランナーを終了し、成果物を公開しない
fi
```

型エラー5件の修正で30ファイル・1,000行の差分が出たら、それは修正ではなく何か別のことが起きています。中身を読むまでもなく破棄してよい——変更量の上限は、diffの内容を1行も理解せずに異常を弾ける、最も安上がりなガードレールです。

## 最後の層: 戻せる備え

ここまでの4層をすべてすり抜けた事故に効く層が、ひとつだけあります。冒頭の実話で実際に筆者を救った層—— **戻せる備え** です。

原則はひとつです。 **エージェントに触らせてよいのは、戻せる領域だけ。**

- 作業対象はgit管理下に置く。gitは「全履歴が残る自動バックアップ」であり、エージェント時代に価値が上がった発明です
- 成果物はPR経由にする（「自律修正ループの設計」の章の原則）。mainへの直接pushと本番へのアクセス権を別途禁止し、保護ブランチのレビュー要件を必須にします。PR経由という運用ルールだけではアクセスは遮断されません
- CIランナーは使い捨てにする。ジョブが環境をどれだけ汚しても、次のジョブはまっさらな環境で始まります
- git管理外でエージェントの手が届く場所（設定ファイル、ローカルの資産）は、バックアップを自動化しておく。筆者の `~/.ssh/config` が30分で戻ったのは、たまたまバックアップがあったからです。「たまたま」を仕組みにします

裏返すと、 **戻せない操作はガードレールで守るのではなく、そもそもエージェントの仕事から外します** 。本番データベースへの直接操作、外部への通知送信、公開APIの本番呼び出し。「なぜ「本番運用」は別物なのか」の章で「向かないタスク」に挙げたものは、権限を絞って恐る恐るやらせるのではなく、設計から排除する。ガードレールの最良の使い方は、ガードレールを試させないことです。

## 同型の事故を減らす — before / after

冒頭の事故に戻って、この章の層を当てはめ直します。左の列が事故当時に存在した守り、右の列がこの章で作った守りです。

| 層 | 事故当時 | 現在 |
| --- | --- | --- |
| お願い | 特になし（事故後にルールを明文化） | ルールは維持しつつ、下の層に降ろした |
| 宣言 | なし | `Edit(~/.ssh/**)` などのdenyをコミット |
| 強制 | なし | プロジェクト外書き込みをブロックするPreToolUseフック |
| 検出 | 症状が出るまで気づけず | 拒否はその場でブロック+記録に残る |
| 備え | たまたまバックアップがあった | git管理+PR経由+設定バックアップの自動化 |

Edit / Writeからの同型の書き込みを、実行前に止める条件ができました。ただし、別のツール経由や設定の不備まで含めて、再発しないと保証するものではありません。未知の形の事故は起きます。層を重ねるのは事故をゼロにする行為ではなく、事故の確率と被害半径を段階的に削る行為です。だからこの表には最後の行——戻せる備え——があり、そしてどの層が働いたかを後から追えるようにしておく必要があります。

その「追える」の設計、そして「事故ではなく、誰かに操られて起こす事故」への守りが、次の「 [セキュリティ](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/security) 」の章のテーマです。この章の道具——permissions・サンドボックス・Hooks・上限——はそのまま持ち越しますが、目的が「やりすぎを止める」から「悪用されても被害を出さない」に変わります。エージェントが読むものはすべて入力である——「なぜ「本番運用」は別物なのか」の章で予告した脅威モデルを、いよいよ正面から扱います。

## まとめ

- 事故は関係ない作業から来る。発生と発覚は分離する。最後に効くのは備え——実体験が教える守りの3原則
- **ルールはモデルではなくハーネスに書く** 。お願い（プロンプト）→宣言（permissions）→強制（サンドボックス・Hooks）の階段で、お願いを順に昇格させる
- permissionsは **deny→ask→allow の順・最初のマッチで決まる** 。パスルールは `Edit()` / `Read()` で書く（ `Write()` は参照されない）。アンカー4種を正確に
- 宣言はBash内の既知ファイルコマンドまで。サブプロセスの穴は **OSサンドボックス** で塞ぐ（Bashと子プロセス全部に強制・denyルールとマージ）
- Hooksは宣言で書けない条件の **自作チェックポイント** 。プロジェクト外書き込みブロックが代表例。宣言で書けるものは宣言で
- 上限は **異常の検出器** 。時間・ターン・コストに加えて変更量（ファイル数・行数）。上限到達はエスカレーション
- 最後の層は **戻せる備え** 。エージェントに触らせるのは戻せる領域だけ。戻せない操作は守るのではなく仕事から外す
