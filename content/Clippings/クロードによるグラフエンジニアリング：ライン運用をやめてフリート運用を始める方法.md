マルチエージェントシステムを構築するほとんどの人は、最終的に直線状のシステムに行き着きます。ステップ1、ステップ2、ステップ3と、それぞれ前のステップが完了するまで待機してから開始します。しかし、これらのステップの半分は、そもそも待機する必要がありませんでした。これはエージェントの問題ではなく、形状の問題です。ボトルネックはモデル自体ではなく、あなたが描いた直線だったのです。

これは、グラフの形状を修正するためのガイドです。読み終える頃には、グラフが実際には何であるか、処理速度を低下させる偽のエッジを見つける方法、あらゆる本格的なエージェントシステムの背後に現れる唯一のパターン、誰も警告してくれないようなグラフの破綻箇所、そしてClaude Codeでたった一文から本物のグラフを構築する方法がわかるようになります。

## グラフエンジニアリングとは実際には何なのか

1か月前は、誰もがループについて話していました。1つのエージェント、1つの指標、試行、確認、調整、そして再実行という1つのサイクル。それが先月のスキルであり、確かに役立ちました。

ループの問題点はグッドハートの法則です。ループは自身の指標しか認識できません。チケット解決率に連動したサポートボットは、問題を解決するのではなく、チケットを素早くクローズすることを学習します。解決率は上昇する一方で、顧客満足度は低下します。ループは目標が正しいかどうかを問うことができません。与えられた数値を追いかけることしかできないのです。

答えは、より良いループではありません。ループのグラフです。単一のエージェントが単一の数値を追いかけるのではなく、サイクルが互いに監視し、修正し合うネットワークです。

エージェントにとって、これはつまり、すべてを一直線に実行する単一のエージェントを作成するのをやめ、作業の構造を設計し始めるということです。何が何より先に実行されるのか。何が同時に実行できるのか。何が他のすべての処理を待つ必要があるのか​​。その構造がグラフです。そして、Claude Codeは、これらを直接構築するためのツールを提供しています。

## 必要な語彙はこれだけ

グラフは正確に2つの部分から構成される。

ノードとは、作業の単位です。エージェントが1つ、境界のあるジョブが1つ、入力されるものが1つ、出力されるものが1つ。競合他社を1社調査する。ファイルを1つレビューする。クレームを1つ確認する。ノードに2つのジョブが割り当てられた瞬間、それは並列化も検証もデバッグもできないものになります。

エッジとは依存関係のことです。つまり、このノードの出力が別のノードの入力となることを示すものです。それ以上でもそれ以下でもありません。エッジは、データが実際にその上を移動する場合にのみ存在します。

ノードが思考を行い、エッジが結果を伝達する。これが全てだ。

グラフにおいてノードを実際に使用可能にする要素は契約です。つまり、限定されたジョブ、定義された入力、スキーマによって強制される定義された出力形状です。出力が自由記述の羅列であるノードは、人間しか読めません。出力形状が固定されているノードは、次のノードが推測することなく利用できるノードであり、それがまさに重要な点です。

```javascript
const ITEM = {
  type: 'object',
  properties: {
    title:  { type: 'string' },
    url:    { type: 'string' },
    impact: { type: 'string', enum: ['high', 'medium', 'low'] },
  },
  required: ['title', 'url', 'impact'],
};

const result = await agent(source.prompt, {
  label:  \`research:${source.key}\`,
  schema: ITEM,
  agentType: 'general-purpose',
});
// result is a shape the next node can trust, not free text
```

## ステップ1：偽の縁を見つける

これは費用がかからず、すぐに効果が得られる方法です。

現在実行しているワークフローを一つ取り上げ、手順ごとに確認してみましょう。各手順で、「この手順は前の手順の結果を必要とするか？」という質問を自問自答してください。もし「必要」であれば、エッジは確かに存在します。順序を維持してください。「必要」でなければ、エッジは存在しません。待機時間は完全に無駄です。これらの2つのジョブは同時に実行できます。

「ファイルAのバグをチェックし、次にファイルBのバグをチェックする。」これは一連の手順のように見えます。しかし、ファイルBのレビューでは、ファイルAが返した内容は一切確認されません。これらの手順が連鎖しているのは、入力した順序によるだけです。これらを並行して実行すると、全体の処理時間は、処理速度の遅い方のファイル1つ分で完了し、2つの処理時間を合計した時間では完了しません。

ほとんどどんな描画ワークフローでも、こうした偽のエッジが2つか3つ見つかるでしょう。それらはすべて、あなたが無料で無駄にしている時間です。

現在お使いの線形エージェントは、既にグラフ構造になっています。ただし、最も簡素なグラフ、つまり各ノードに1つの入力矢印と1つの出力矢印を持つ単一の鎖です。動作は正しいのですが、動作が遅いです。また、鎖には冗長性がないため、いずれかのノードが停止すると、下流の処理はすべて停止してしまいます。

グラフエンジニアリングにおける最初の真のスキルは、その連鎖を描き直すことです。データを持たない矢印を切断すると、線はより広いものへと収束します。それは、すべて同時に実行できるいくつかの独立したジョブであり、それらすべてを必要とする1つのジョブにデータを提供します。40ステップの直線的なワークフローでは、40箇所の連続的な障害が発生し、その40箇所すべての遅延が合計されます。グラフとして描かれた同じ40個のジョブは、実際に存在する依存関係の数（通常は3～5個）だけを持ち、すべての遅延の合計ではなく、最も遅いレイヤーの速度で完了します。

## ステップ2：あらゆる本格的なエージェントシステムの背後にある一つのパターン

本格的なエージェントシステムがどのように動作するかを見てみると、同じようなパターンが繰り返し現れます。作業が分割され、複数の作業員が同時に作業を進めます。そして、彼らが発見したものを何らかの方法で確認し、最終的にすべてが統合されて一つの答えにたどり着きます。

その図はダイヤモンドと呼ばれています。その正式名称は覚えておくと良いでしょう。「扇状に広げる、縮める、合成する」。

情報を広げて全体像を把握する。シンプルなコードで情報を圧縮する。最終的なエージェントで合成して答えを生成する。

Claudeに搭載されている調査機能は、まさにこの仕組みを本番環境で実行しています。リーダーが調査の方向性を定め、作業員が並行して集まり、調査結果が検証され、最終的に一つのレポートがあなたの手元に届きます。

クロードが書いたダイヤモンドは、こんな感じです。

```javascript
const angles = [
  "pricing vs the top 3 competitors",
  "what buyers complain about in reviews",
  "the feature gaps in the category",
  "where the market moves in the next 12 months",
];

// FAN OUT -- one researcher per angle, all at the same time
const raw = await parallel(
  angles.map(a => () => agent({
    task: \`research: ${a}. every claim needs a source url and date.\`,
    schema: Finding,
    model: "cheap",
  }))
);

// REDUCE -- plain code, no model, no tokens
const findings = dedupeBySource(raw.flat().filter(Boolean));

// VERIFY -- a fresh skeptic per finding, tries to kill it
const survivors = await parallel(
  findings.map(f => () => agent({
    task: "try to disprove this. return keep or drop and why.",
    input: f,
    freshContext: true,
    model: "strong",
  }))
).then(v => findings.filter((_, i) => v[i].verdict === "keep"));

// SYNTHESIZE -- one agent writes the answer from what survived
return agent({
  task: "one report, ranked by confidence, sources attached.",
  input: survivors,
  model: "strong"
});
```

一度読めば、その仕組み全体が理解できる。作業が独立して展開されるファンアウト。モデルトークンを使わずにフリーコードで実行される削減。新しいコンテキストでの検証。退屈なノードには安価なモデル、判断が下される強力なノードには強力なモデル。最後には単一の合成。

市場調査、コードレビュー、調査レポート、いずれも基本的な構造は同じだ。視点や指示を変えれば、形は変わらない。

ダイヤモンドの形が見えるようになれば、「エージェントにもっと多くのステップを実行させるにはどうすればいいか」という問いは消え、「どこで分割し、どこで統合するか」という問いに変わります。この2つ目の問いこそが、スケールアップを可能にするのです。

## ステップ3：最初のグラフを作成する

理論はもう十分だ。実際に使えるリポジトリを開いて、これをClaude Codeに貼り付けてみよう。

```text
Create a workflow to audit every route file under src/routes/
for missing auth checks. Spawn one agent per file, then run an
independent verifier on each finding before reporting.
Analyze a maximum of 20 files to start.
```

src/routes/ を、ファイルの保存場所に置き換えてください。「max 20」は、初回実行時のコストを抑えるためのものです。

何が起こるか見てみましょう。Claude Codeは「ワークフロー」を強調表示し、通常のチャットではなくグラフが構築されていることを示します。JavaScriptオーケストレーションスクリプトを作成し、実行前に各フェーズを表示します。内容を確認して承認してください。

次に、処理群が実行されます。ファイルごとに1つのエージェントが同時に実行され、セッションは解放されたままです。/workflowsと入力すると、スコープ、ファンアウト、検証、合成といった処理をリアルタイムで確認できます。

最終的に得られるのは、20件もの個別のチャット履歴を一つ一つ確認する必要のない、たった一つのレポートです。中間結果はスクリプトの変数内に格納され、ユーザーのコンテキストには一切表示されません。

これはグラフです。たった1つの文から12個のエージェントが生まれます。実行がうまくいったら、sキーを押してください。.claude/workflowsに保存され、名前でいつでも再実行できる単一のコマンドになります。タスクを変更しても、形状は維持されます。

## ステップ4：検証ツールこそが鍵だ

ほとんどの人は、ファンアウト図を描いてそれで終わりにしてしまう。それは高価なおもちゃのようなものだ。本当のグラフは、重要なすべてのエッジにチェッカーが描かれている。

AIの自己評価に関するあらゆる本格的なテストは、同じことを示しています。つまり、モデルは自身のミスのほとんどを見落としてしまうということです。モデルが自身の作業を採点すると、どうしても甘くなりすぎてしまいます。ですから、作業を行ったエージェントに作業内容をチェックさせるべきではありません。

エッジに別のノードを配置します。そのノードの唯一の役割は、検出結果が下流に進む前に排除することです。生き残れば通過し、そうでなければその場で消滅します。

誰も指摘しない落とし穴はここにある。検証器にはクリーンなコンテキストが必要だ。作業者と同じ会話を与えても、何もチェックされない。ただ違うフォントでうなずいているだけだ。1つのコンテキストを共有するエージェントのグラフは、衣装を着た単一のループに過ぎない。同じように壊れるが、より遅く、よりコストがかかり、途中で緑色のランプがはるかに多く点灯する。

つまり、検証者は新しいノードです。独自のコンテキストを持ちます。実際の信号をチェックし、「エージェントが完了したと言ったかどうか」ではなく、「テストが実際に合格するかどうか」を確認します。10個の同一のチェックでは見逃してしまうものを、3つのレンズで捉えます。正しいか？最新か？ソースは本物か？すべての発見に対して、これら3つを並行して実行します。懐疑論者の大多数が容認するものだけを残します。

```javascript
const verdicts = await parallel(
  ['correctness', 'recency', 'source-validity'].map(lens => () =>
    agent({
      task: \`judge this finding via ${lens}. return keep or drop.\`,
      input: finding,
      freshContext: true,
      schema: { verdict: { enum: ['keep', 'drop'] } }
    })
  )
);

const passes = verdicts.filter(v => v.verdict === 'keep').length >= 2;
```

覚えておくべきルールは、ワーカーとその検証者がコンテキストを共有してはならないということです。共有した瞬間、ループが自身の宿題を採点するという、より高額な問題に逆戻りしてしまいます。

## ステップ5：仕事の規模がわからない場合

作業の規模が実際に作業に取り掛かるまで分からないため、事前にグラフを計画できない場合もあります。例えば、バグの調査で1つのバグが見つかると、さらに3つのバグが発見されるといったケースです。また、依存関係の監査で1つのスレッドを引っ張ると、他の10個のスレッドが絡み合ってしまうといったケースもあります。

そのためにはサイクルが必要だ。つまり、検索が尽きるまで、前のノードに戻る制御されたエッジが必要となる。

収束するパターンは、何も見つからないまでループすることです。2回連続で新しいものが見つからないまでファインダーを生成し続け、その後停止します。

成否を分ける重要な要素であり、ほとんどの人が最初に犯す間違いは、重複排除の対象です。確認済みの結果だけでなく、検出されたすべてのものに対して重複排除を行う必要があります。そうしないと、却下された結果が毎回再出現し、ループが途切れることなく、同じ行き止まりを永遠に再発見するために報酬を支払う機械を構築してしまうことになります。

```javascript
const seen = new Set();
const confirmed = [];
let dry = 0;

while (dry < 2) {
  const found = (await parallel(
    FINDERS.map(f => () => agent(f.prompt, { schema: BUGS }))
  )).filter(Boolean).flatMap(r => r.bugs);

  const fresh = found.filter(b => !seen.has(key(b)));
  if (!fresh.length) { dry++; continue; }
  dry = 0;

  // dedupe against SEEN, not confirmed -- this is the detail that matters
  fresh.forEach(b => seen.add(key(b)));

  const verified = await parallel(
    fresh.map(b => () => agent(
      \`is this real: ${b.desc}\`, { schema: VERDICT }
    ))
  );

  confirmed.push(
    ...verified.filter(v => v.real).map((v, i) => fresh[i])
  );
}
```

本番環境では、ループの停止条件は3つあります。2回の試行が失敗に終わる、予算が固定される、または反復回数が最大になる、のいずれかです。これら3つすべてが同時に発生すると、問題が発生します。どれか1つだけでも、罠にはまる可能性があります。

## レイテンシを制御するトポロジー

グラフの形状は見た目の問題ではありません。それは実行時間に影響を与える最大の要因であり、誰もが迷うのはparallel()とpipeline()のどちらを選ぶかという点です。

parallel() バリアを使用すると、次のステージが開始される前に、すべての処理が最も遅いノードの処理完了を待つことになります。すべての処理は、最も時間がかかる処理の後ろで待機します。例えば、9 つのエージェントが 2 秒で処理を完了し、1 つのエージェントが 20 秒かかる場合、バッチ全体が 20 秒間待機してから合成が開始されます。

pipeline() は、各アイテムをすべてのステージに独立して、何の障壁もなくストリーミングします。アイテム A がステージ 3 にいる間に、アイテム B はまだステージ 1 にいるといったことが可能です。処理速度の速いアイテムは、処理速度の遅いアイテムの後ろで待機することなく、早く処理を完了します。

デフォルトでは pipeline() を使用します。バリアを使用するのは、ステージがすべての以前の結果を一度に必要とする場合に限ります。例えば、クロスセットの重複排除、合計値での早期終了、「その他の結果」との比較プロンプトなどです。直感的に判断すると、並列処理、変換処理、並列処理の順に記述し、中間の変換処理にアイテム間の依存関係がない場合、パイプラインを使用してバリアを完全に省略すべきでした。バリアによる遅延は実際に発生し、測定可能であり、無駄です。

```javascript
// barrier -- everything waits for the slowest node
const results = await parallel(jobs);
// one slow agent holds the whole batch

// pipeline -- items flow through independently
const results = await pipeline(jobs, stages);
// fast items finish early, slow ones catch up without blocking
```

## ステップ6：グラフが実際に途切れる箇所

実際のグラフ作成において、3つの失敗が大きな障害となることが多い。構築する前に、これらの失敗を知っておくべきだ。

**コンテキストの崩壊。1000**個のノードを分岐させ、そのすべての出力を最終ステップに投入しようとすると、合成が始まる前にコンテキストウィンドウを超えてしまいます。分岐処理を段階的に行いましょう。結果をバッチ処理し、各バッチを要約し、要約を結合します。最終ステップでは、1000個の生の出力ではなく、25個の要約を読み取ります。

```javascript
const batches = chunk(results, 40);
const summaries = await parallel(
  batches.map(b => () => agent({ task: "summarize this batch", input: b }))
);
return agent({ task: "write the answer from the summaries", input: summaries });
```

**見かけ上の独立性。2**つのノードは、プロンプトで互いについて言及しないため、独立しているように見えますが、実際には両方とも同じファイルに書き込んだり、同じレート制限付きAPIにアクセスしたりしています。これは隠れた利点です。Bunのチームが最初に大規模なポートを多数のエージェントに分散させたとき、1つのワークスペースを共有し、互いに上書きし合っていました。各ワーカーに独自のgitワークツリーを与えましょう。

```javascript
await parallel(files.map(f => () => agent({
  task: \`refactor ${f}\`,
  worktree: true,
})));
```

**サイレントノード障害。**チェーンでは、1つの障害で全てが停止し、厄介ではあるものの、すぐに気づくことができます。グラフでは、200個のノードのうち1つが故障していると、一見完全なレポートに紛れ込んでしまう可能性があります。マージの各ステップでは、入力値を期待値と比較して、不足している箇所を特定する必要があります。

```javascript
const results = (await parallel(jobs)).filter(Boolean);
if (results.length < jobs.length) {
  flag(\`WARNING: ${jobs.length - results.length} nodes returned nothing\`);
}
```

## 今週作成するグラフ6つ

それぞれが同じダイヤモンドですが、それぞれ異なるタスクをターゲットにしています。Claude Codeを実際のフォルダで開き、括弧内の部分を入れ替えて貼り付けてください。「workflow」という単語は、Claudeに単一の手順ではなく、連携した一連のプロセスを構築するように指示するものです。

**意思決定に役立つ調査。**

```text
workflow: decision-grade research on [your question]
fan out into 5 distinct angles, one researcher per angle, in parallel
every finding needs a source link and a date
a skeptic attacks each finding and tries to disprove it, drop what fails
survivors into one report ranked by confidence
save to research-report.md
change nothing after that without asking me
```

**セキュリティチェック。**

```text
workflow: audit every route file under src/routes/ for missing auth checks
one agent per file, in parallel
an independent verifier on each finding with fresh context
cap at 20 files on this first run
report how many files came back so nothing fails silently
```

**コードベースのリファクタリング。**

```text
workflow: find every function over 100 lines and propose a refactor for each
one agent per file, in parallel
an independent checker on each proposed refactor with fresh context
dedupe proposals against everything already seen
cap at 50 files on this first run
```

## 誰も使わないモデル階層化

すべてのノードに最適なモデルが必要なわけではありません。グラフは、単一のエージェントでは決して示されない方法で、このことを明確に示します。

ノードの中には、範囲が限定され、繰り返し実行されるものがあります。例えば、「このフィールドを抽出する」「このチケットを分類する」「このソースを確認する」などです。また、実際の判断を下すノードもあります。例えば、「レポートをまとめる」「調査結果を裁定する」「最終回答を記述する」などです。

退屈なノードはより安価なモデルで実行し、高価なトークンは実際に判断を下す必要がある箇所で使いましょう。大規模な実行の前に /model を確認し、ファンアウトの繰り返しノードを下位にルーティングして、マージノードは上位に維持します。これが、トークンを大量に消費するグラフを、その形状を変えることなく、コスト効率の良いものに変えるための鍵となります。

## グラフが間違った答えである場合

ほとんどのグラフ工学の記事が省略する部分がここにある。なぜなら、この部分は技術の魅力を伝えるものではないからだ。

グラフは視野を広げるツールではあるが、判断力を高めるものではない。グラフは視野を広げ、一度に複数の独立した作業を行うためのツールだ。作業範囲が広くない場合、そもそもグラフ自体が問題なのではなく、グラフを追加しても失敗する可能性が増えるだけだ。

大学でプロセス図に関する授業を丸々受講しました。何週間もかけて、作業をグラフとして表現し、できるだけ効率的にする方法を学びました。当時は抽象的な概念に感じましたが、今ではまさにAIエンジニアたちが真剣に議論するテーマとなっています。そして、その授業で最も難しかったのは、グラフの作成方法ではなく、グラフを作成すべきでない時を知ることでした。

タスクが小さいか孤立している場合はスキップします。バグを 1 つ修正したり、機能を 1 つ追加したりする場合です。調整は単なるオーバーヘッドであり、単一のエージェントの方が速くて安価です。厳密な監視が必要な場合はスキップします。次の実行の前にすべてのステップを読み、承認したい場合、グラフの目的全体が逆効果になります。まだ何を探しているかわからない場合はスキップします。探索作業には、計画に固定されたフリートではなく、操縦できる 1 つのエージェントが必要です。ステップが本当に相互に依存している場合はスキップします。すべてのステップが前のステップの出力を読み取る場合、並列化するものは何もありません。

その決め手は、ステップ1の偽エッジテストです。間にエッジを持たない2つのジョブが見つからない場合、構築すべきグラフは存在しません。それはループであり、ループは問題ありません。実際に実行されるループは、誰にも感銘を与えず、完了に時間がかかるグラフよりも価値があります。

## グラフの正確性を保つアンカー

トポロジーだけでは真実は得られない。

完全なグラフを構築したと想像してみてください。検証者と監査ノードがペアになり、すべてのノードが互いを監視します。そして、監査ノードは、そもそも同じシステムから生成された財務システムと数値を照合します。すべてが一貫しています。何も検証されていません。このグラフは、単一ループの場合とまったく同じように失敗しますが、失敗のタイミングが遅く、コストが高く、失敗に至る過程で緑色のランプがはるかに多く点灯します。

グラフにはアンカーとなる要素、つまり議論の余地のないノードが必要です。「合格するはず」ではなく、実際に実行されたテストが合格したこと。銀行口座に入金された収益。実際に継続利用してくれた顧客。そして、最適化ツールが弱めたくなるようなルールは、まさに勝利のために曲げようとするルールだからこそ、変更できないように固定しておく必要があります。

グラフの正直さは、その中に含まれる、動かない要素の正直さに左右される。反論できない数字に基づいて判断すれば、グラフは地に足をつけている。しかし、グラフ自身に報告書を採点させれば、自信満々に間違っていると断言するだろう。

## 実際にかかる費用と、正しい始め方

グラフは通常のチャットよりもコストがかかる。調整コストは下がるが、作業自体のコストは変わらない。エージェントは依然としてトークンを消費し、多数のエージェントが集まれば大量のトークンを消費する。

最も分かりやすい公開例としては、あるエンジニアがこのシステムを使ってBunランタイムを書き換え、約53万5000行のZigコードを約11日間で100万行以上のRustコードに変換した事例がある。手作業で同じ作業を行うと、ほぼ1年かかる。このシステムは最大64個のエージェントを同時に稼働させ、約50のワークフローを実行した。また、使用料は約16万5000ドルかかり、全体の設計と監視には人間が必要だった上、これほど多くのAIコードが安全にレビューできるのかという批判も浴びた。

あれが限界だ。ここからが本当のスタート地点だ。

20項目を上限とするグラフを1つ実行します。次のグラフを実行する前に、使用状況レポートを確認してください。次の3つの質問を自問してください。ファンアウトによって、単一のエージェントでは得られなかった成果が得られましたか？検証ツールは、ワーカーが見逃した何かを検出しましたか？その結果は、コストに見合うものでしたか？

3つの質問すべてに「はい」と答えた場合は、上限を2倍にします。そうでない場合は、幅を広げる前に形状を修正します。20個のアイテムでコストを回収できるグラフは、200個のアイテムでも回収できます。20個のアイテムで回収できないグラフは、2000個のアイテムでも回収できず、それを知るには100倍のコストがかかります。

まずはキャップを装着する。コストに注意する。スケールを獲得する。

## シフト

プロンプターが質問をする。建築家がグラフを描く。

直線的な操作方法は、決して究極の形ではなかった。それは単なる最初の形であり、誰もが最初に手に取る形だった。なぜなら、それは私たちのタイピングの仕方に合致していたからだ。一行ずつ、一文字ずつ、一度に一つのことだけを。

ノードとエッジが見えるようになったら、エージェントにそれ以上のことを要求するのではなく、グラフ全体に処理範囲を広げるようにします。作業が独立している箇所では、グラフを扇状に広げます。信頼性が重要な箇所では、エッジをゲートします。真実を保持するノードは固定します。判断が不要な箇所では、モデルを階層化します。

ほとんどの人は、手順を順番に並べ続けるだろう。

グラフの描き方を習得した者は、艦隊を率いることになるだろう。そして、彼らは他の者たちが陥っている限界に気づくことはないだろう。
