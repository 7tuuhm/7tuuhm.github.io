## サブエージェント編成 — コンテキストを分割統治する

[

はんぺん

2026.09.14に更新

](https://zenn.dev/hampen2929)

前の章までで、1本の自律修正ループが毎晩回るようになりました。ここから対象を広げていく——修正の種類を増やす、調査の深いタスクを任せる、リファクタリングに手を出す——と、今までと質の違う壁に当たります。

エージェントの **コンテキストウィンドウ** です。

この章は、1つのコンテキストに収まらない仕事を、複数の小さなエージェントに分割統治させる設計を扱います。道具としてはClaude Codeのサブエージェント機能を使いますが、本質は道具の使い方ではなく、 **仕事の切り方** です。

## なぜ分けるのか — 長いセッションは後半から壊れる

コンテキストウィンドウは、エージェントのワーキングメモリです。読んだファイル、実行したコマンドの出力、途中の試行錯誤——すべてがここに積まれ、上限に近づくほど劣化が始まります。

長時間タスクの失敗パターンは、だいたい次の形をとります。

- **序盤の指示を忘れる** 。最初のプロンプトで指定した禁止事項が、大量のファイル内容に埋もれて効かなくなる
- **目的がずれる** 。調査のつもりが、調査中に見つけた別の問題の修正を始めている
- **後半の品質が下がる** 。同じセッションの1件目の修正は丁寧なのに、8件目は雑になる

対話利用なら「一回セッションを仕切り直すか」で済む話です。しかし無人運用では、誰も仕切り直してくれません。ここで思い出してほしいのが、「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で置いた原則——1回の完成度ではなく反復の安定性——です。あれのコンテキスト版が本章の主題になります。 **セッションは長くなるほど脆い。だから、短いセッションの組み合わせで仕事を構成する。**

分け方には2軸あります。 **時間で分ける** （計画と実行を別セッションにする）と、 **役割で分ける** （調査・実装・レビューを別エージェントにする）。順に見ていきます。

## 道具の確認 — サブエージェントとは何か

先に道具を押さえます。Claude Codeのサブエージェントは、 **独立したコンテキストウィンドウを持つ子エージェント** です。親エージェントはタスクを依頼し、子は自分のコンテキストで作業して、 **結果の報告だけ** を親に返します。

この「報告だけが返る」が要点です。子が調査で50ファイル読んでも、親のコンテキストに積まれるのは報告書の数百行だけ。コンテキストの汚染が子の中に封じ込められます。

![1つの長いセッションではコンテキストが積み上がり劣化する。分割統治では汚染が子の中に封じ込められ、報告だけが親に返る](https://static.zenn.studio/user-upload/deployed-images/29db6f2de6166e0bd739c7af.jpg?sha=089e2e78e5ca504350fb97aaf00e51f5d890e752)

図は、子が調査から検証までを担う一般形として描いています。本章の実例では役割をもう少し狭く取り、修正役が持つのはReadとEditだけで、検証は後段のCIが行います。図のどの箱を子に任せるかは、章末の実例で確かめてください。

定義は `.claude/agents/` にMarkdownファイルを置くだけです。

```
---
name: investigator
description: 失敗の原因調査を担当。コードを読み、原因と修正方針を報告書にまとめる
tools: Read, Grep, Glob
model: inherit
---

あなたは調査専任のエージェントである。
依頼された失敗・エラーについて、関連コードを読んで原因を特定し、
「原因 / 根拠（ファイルと行） / 修正方針 / 影響範囲」の形式で報告する。
修正はしない。修正方針の提案までが仕事である。
```

frontmatterで押さえるべきフィールドは4つです。

| フィールド | 役割 |
| --- | --- |
| `name` / `description` | 識別子と、どういうときに任せるかの説明 |
| `tools` | このエージェントが使えるツールの許可リスト |
| `model` | このエージェントが使うモデル（省略時は親を継承） |
| `maxTurns` | このエージェントのターン上限 |

注目してほしいのは `tools` と `maxTurns` です。つまりサブエージェントは、コンテキストの分割と同時に、 **「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」の章でやる権限と上限の設計を役割単位で宣言する場所** でもあります。調査係は読み取り3ツールしか持たない——ファイル1枚でそれが強制されます。

ヘッドレス実行では2つの渡し方があります。`.claude/agents/` はプロジェクトの資産としてコミットしておく方法（ `--bare` では自動読み込みされないので注意）と、 `--agents` フラグでJSON定義を直接渡す方法。CIでは後者か、 `--bare` に定義ファイルを明示的に組み合わせます。さらに `--agent <name>` を使うと、 **セッション全体をそのエージェントとして起動** できます。この最後のやつがCIでは主役になります（後述）。

## 時間で分ける — Plan→Execute分離

分割の1軸目は時間、つまり **計画と実行を別セッションにする** ことです。

なぜ混ぜてはいけないのか。計画と実行では、コンテキストの使い方が正反対だからです。計画は「広く読む」——多くのファイルを浅く読み、全体像を掴む。実行は「狭く書く」——対象ファイルだけを深く見て、正確に変更する。1セッションで混ぜると、探索で膨らんだコンテキストを引きずったまま実装することになり、冒頭で挙げた失敗パターンの典型になります。

ヘッドレス実行でのPlan→Executeは、 `claude -p` を2回に分ける形になります。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__d73cc4b23d898" frameborder="0"></iframe>

1段目は読み取り専用の権限で計画だけを立てさせ、 `--json-schema` で構造化した計画（対象ファイル、変更内容、理由）をファイルに保存します。2段目は計画を入力として渡し、「この計画を実施せよ。計画にない変更はするな」で実行します。図の中央にある機械ゲートが、この章で新しく足す部品です。2つの `claude -p` は直接つながらず、間に保存された計画とその検査が挟まります。

わざわざ分ける利点は、コンテキストの分離だけではありません。 **計画がファイルとして残る** ことが、無人運用では効きます。

- **止められる**: 計画と実行の間に機械ゲートを挟めます。変更対象が想定スコープ外なら、実行前に止まる。「自律修正ループの設計」の章では実行後の差分を検査しましたが、計画段階で止めれば無駄なコストも払いません
- **遡れる**: 事故調査のとき「なぜこの変更をしたか」の一次資料になります（「 [セキュリティ](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/security) 」の章の監査証跡につながります）
- **やり直せる**: 実行だけ失敗したら、計画を立て直さず実行だけリトライできます。計画は高い（広く読む）、実行は安い（狭く書く）ので、この分離はコスト面でも合理的です

対話モードには計画モード（ `--permission-mode plan` ）という専用の仕組みもありますが、CIでは上記のように「読み取り専用権限の1段目」として自作するほうが、ゲートを自由に設計できて実務的です。

## 役割で分ける — 調査・実装・レビューの最小編成

分割の2軸目は役割です。といっても、いきなり大所帯を作る必要はありません。無人運用でまず効くのは3役です。

| 役割 | tools | 仕事 |
| --- | --- | --- |
| investigator（調査） | Read, Grep, Glob | 広く読んで報告書を書く。書き込み権限なし |
| implementer（実装） | Read, Edit | 計画・報告書に従って狭く直す。検証はCIへ渡す |
| reviewer（レビュー） | Read, Grep, Glob | 差分を契約（禁止事項・スコープ）と照らして所見を返す |

それぞれの `tools` が仕事の定義そのものになっていることに注目してください。調査係とレビュー係は構造的に書き込めません。「調査だけしてと言ったのに直し始めた」という事故が、プロンプトのお願いではなくツール権限で封じられます。

実装とレビューを分ける理由は、人間のコードレビューと同じです。 **自分の変更を自分で採点させない。** 同じコンテキストで書いたエージェントは、自分の判断の前提ごと引き継いでレビューするので、前提の間違いを見つけられません。別コンテキストのレビュアーは、差分と契約だけを見ます。ただし勘違いしないでほしいのは、AIレビュアーは一次受けであって最終判定者ではないことです。合否を決めるのは全体再実行の機械検証と人間のマージ——この構造は「自律修正ループの設計」の章から変わりません。

CIでの使い方は、自動委譲に頼らず **段ごとに `--agent` で役割を固定する** のが基本形です。

調査の段では `--agent planner` 、実装の段では `--agent fixer` と指定します。 `--agents` で定義を渡し、調査結果をJSONで保存してから実装へ渡す例を、この章の後半に載せます。

対話モードでは「Claudeが必要に応じてサブエージェントに委譲する」使い方が便利ですが、無人運用では委譲判断そのものが非決定性の源になります。CIの各ステップに役割を1つずつ割り当てれば、 **どの段がどの権限で動いたか** がワークフロー定義から静的に読めます。監査の壁への答えが、またひとつ増えました。

ここで用語を1つ区別しておきます。 `--agent` で起動したセッションは、親から委譲された子エージェントではなく、それ自体が独立した主セッションです。PlanとExecuteは別々の `claude -p` として走るので、結果JSONも `total_cost_usd` も呼び出しごとに別に返り、自動では合算されません。ジョブ全体の費用はワークフロー側で足し合わせます。1回の `claude -p` の中で親が子に委譲した場合との集計の違いは「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」の章で扱います。

役割を増やしすぎないことも編成の一部です。役割が増えるほど、受け渡しのたびに情報が落ちます（報告書に書かれなかった文脈は、次の役割には存在しません）。3役で回るうちは3役で。エージェントの組織を本格的に設計し、育てていく話は、本書の続刊として構想している「AIチーム開発」の主題なので、そちらに譲ります。

## モデルの使い分け — 判断の幅で選ぶ

役割を分けると、モデルの使い分けが自然にできるようになります。frontmatterの `model` フィールドが役割ごとにあるからです。

選び方の軸は、料金表ではなく **タスクの判断の幅** です。

| 判断の幅 | タスクの例 | モデル |
| --- | --- | --- |
| 広い（正解が一意でない） | 原因調査、計画立案、レビュー所見 | 上位モデル |
| 狭い（合否が機械判定できる） | 計画に従った修正、ログ要約、定型レポート | 軽量モデル |

直感に反するかもしれませんが、 **実装より調査・計画に良いモデルを使う** のがセオリーです。実装の失敗は検証ゲートが拾ってくれますが、計画の失敗は「筋の悪い計画が検証を通ってしまう」形で現れ、機械では拾えないからです。ゲートで守られている段は軽く、ゲートの上流は厚く。

指定方法は `model: sonnet` のようなエイリアスか、モデルIDのフル指定、そして `inherit` （親と同じ・デフォルト）です。エイリアスと実体の対応はモデルの世代交代で変わるので、固定したい場合はフルIDで書きます。費用の測り方は「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」の章で扱います。本書には役割別モデルの比較実測は載せていないため、選択は自分の代表タスクで検証してください。

## 実例 — 夜間ジョブをPlan→Executeに分ける

「自律修正ループの設計」の章の型エラー修正ジョブを、この章の道具で2段化してみます。変わるのはFix周辺だけなので、差分の形で示します。

この実例では調査・計画役を `planner` 、実装役を `fixer` と名付け、独立したAIレビュー段は追加しません。合否は前章のVerifyと人間のレビューで決めます。

まず役割定義です。CIから `--agents` で渡せるよう、JSONで1ファイルにまとめます。

```
{
  "planner": {
    "description": "型エラーの修正計画を立てる。修正はしない",
    "prompt": "渡された型エラーについて関連コードを読み、エラーごとに修正計画（対象ファイル・変更内容・理由）か、直せない理由を出力する。禁止事項: テスト・設定変更を計画に含めること",
    "tools": ["Read", "Grep", "Glob"],
    "maxTurns": 30
  },
  "fixer": {
    "description": "計画に従って修正する。計画にない変更はしない",
    "prompt": "渡された修正計画を実施する。計画にないファイルには触れない。検証は後段のCIが行う。結果は指定スキーマのfixedとskippedで報告する",
    "tools": ["Read", "Edit"],
    "maxTurns": 40
  }
}
```

計画用のスキーマも保存します。修正報告用は前章の `typefix-schema.json` を再利用します。 `fixes` の `maxItems` と `additionalProperties: false` に注目してください。件数の上限と、計画に余計なフィールドを混ぜないことを、出力側の契約として書いています。

```
{
  "type": "object",
  "properties": {
    "fixes": {
      "type": "array",
      "maxItems": 5,
      "items": {
        "type": "object",
        "properties": {
          "file": {"type": "string"},
          "change": {"type": "string"},
          "reason": {"type": "string"}
        },
        "required": ["file", "change", "reason"],
        "additionalProperties": false
      }
    },
    "reason": {"type": "string", "description": "計画の要約。修正不能ならその理由"}
  },
  "required": ["fixes", "reason"],
  "additionalProperties": false
}
```

ワークフローのFixステップは、3ステップに置き換わります。以下は前章のジョブ内へ挿入する抜粋です。Claude Codeのインストールをこの3ステップの前に移し、後の「ガードレール」章の設定と実行可能なフックも用意します。認証は各AIステップにだけ渡します。

読むときは、PlanとExecuteで `--tools` が違うこと、Gateだけが `ANTHROPIC_API_KEY` を持たないこと、この2点を先に確かめてください。役割ごとの権限の差と、ゲートがAIを呼ばない決定的な処理であることが、そこに表れています。

```
# 段A: 計画（読み取り専用）
- name: Plan
  if: steps.detect.outputs.typecheck != '0' && steps.dedupe.outputs.skip != 'true'
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  run: |
    claude --bare -p "$(cat /tmp/errors.txt)" \
      --agents "$(cat .github/agents.json)" --agent planner \
      --tools "Read,Grep,Glob" --allowedTools "Read,Grep,Glob" \
      --settings .claude/settings.json --permission-mode dontAsk \
      --output-format json --max-turns 30 --max-budget-usd 0.60 \
      --json-schema "$(cat .github/schemas/plan-schema.json)" > /tmp/plan.json
    jq -e '
      .type == "result" and .subtype == "success" and .is_error == false
      and (.structured_output.fixes | type == "array")
    ' /tmp/plan.json > /dev/null

# ゲート: 計画を実行前に機械検査
- name: Gate
  if: steps.detect.outputs.typecheck != '0' && steps.dedupe.outputs.skip != 'true'
  run: |
    # 検出はあるのに修正計画が0件なら、修正不能として報告する。
    if ! jq -e '.structured_output.fixes | length > 0 and length <= 5' /tmp/plan.json > /dev/null; then
      jq -r '.structured_output.reason' /tmp/plan.json >> "$GITHUB_STEP_SUMMARY"
      exit 1
    fi
    jq -e '
      all(.structured_output.fixes[];
        .file | startswith("src/") and endswith(".ts")
        and (endswith(".test.ts") | not) and (endswith(".spec.ts") | not)
        and (split("/") | all(. != ".." and . != "." and . != ""
          and . != "tests" and . != "__tests__")))
    ' /tmp/plan.json > /dev/null

# 段B: 実行（計画のみを実施）
- name: Execute
  if: steps.detect.outputs.typecheck != '0' && steps.dedupe.outputs.skip != 'true'
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  run: |
    claude --bare -p "修正計画: $(jq -c '.structured_output' /tmp/plan.json)" \
      --agents "$(cat .github/agents.json)" --agent fixer \
      --tools "Read,Edit" --allowedTools "Read,Edit(src/**)" \
      --settings .claude/settings.json --permission-mode dontAsk \
      --output-format json --max-turns 40 --max-budget-usd 0.60 \
      --json-schema "$(cat .github/schemas/typefix-schema.json)" > /tmp/fix.json
    jq -e '
      .type == "result" and .subtype == "success" and .is_error == false
      and (.structured_output.fixed | type == "array")
      and (.structured_output.skipped | type == "array")
    ' /tmp/fix.json > /dev/null
```

Gateの `length <= 5` は、スキーマの `maxItems: 5` と同じ条件を二重に書いています。無駄ではありません。スキーマ適合はモデル側の出力契約で、Gateはワークフロー側の検査です。どちらか一方の設定が外れても、もう一方で止まります。「自律修正ループの設計」の章でプロンプトの禁止事項を差分検査で裏付けたのと同じ二層の考え方です。

計画のパス検査は文字列上の範囲確認です。リンク先まで保証するものではないため、フックによる解決済みパスの検査と、実行後のVerifyも必要です。計画JSONは命令文を含み得るAI出力として扱い、それを渡しただけで権限を広げないようにします。

後段のVerify（全体再実行と差分検査）とPR作成は前章のままです。検出0件なら3ステップともスキップし、検出があるのに計画できない場合は失敗報告で終わります。二段化で何が変わったかを整理すると——計画がアーティファクトとして残る、実行前にスコープ検査が入る、各段の権限が役割定義に固定される、失敗時に実行だけやり直せる。かかる手間は、JSONファイル1枚とステップ2つ分です。

## いつ分けるべきか — 兆候が出るまで分けない

最後に、逆向きの助言を置きます。 **最初から分けないでください。**

前章の1段構成で安定して回っているジョブを、先回りして二段化する必要はありません。分割は受け渡しの設計というコストを持ち込むので、必要になる前に払うと単に複雑さが増えます。分けるべき兆候は観測できます。

- `num_turns` がじわじわ増えている（試行錯誤が長くなっている）
- 後半に処理された項目ほど、修正の質が落ちる・skipが増える
- 1ジョブのコストが上がり、どの工程で使ったのか分からない

これらが出たら、この章に戻ってきてください。 **編成はスケールの問題への答え** であって、最初の1本のループに必要なものではありません。

## まとめ

- 長いセッションは後半から壊れる。無人運用は **短いセッションの組み合わせ** で構成する。分け方は時間（Plan→Execute）と役割（調査・実装・レビュー）の2軸
- サブエージェントは独立コンテキストの子エージェント。 **報告だけが親に返る** のでコンテキスト汚染が封じ込められ、 `tools` / `model` / `maxTurns` を役割単位で宣言できる
- Plan→Executeの価値は **計画がファイルとして残る** こと。実行前ゲート・監査証跡・実行だけのリトライが手に入る
- 役割の最小編成は3役。実装とレビューは **別コンテキスト** に分け、自分の変更を自分で採点させない。CIでは自動委譲に頼らず `--agent` で段ごとに役割を固定する
- モデルは **判断の幅** で選ぶ。ゲートで守られた実装は軽く、ゲート上流の調査・計画は厚く
- ただし、 **兆候が出るまで分けない** 。編成はスケールの問題への答え

これで第1部「土台」は完成です。ループは回り、編成でスケールもする。しかし今のところ、このシステムの安全は「プロンプトのお願い」と「いくつかの機械チェック」に頼っています。第2部は守りの話——まず「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」の章で、事故を仕組みで防ぎます。あの `~/.ssh/config` の話の続きは、そこでします。
