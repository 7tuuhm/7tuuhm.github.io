## リポジトリの全体像

題材は、ここまで各章で使ってきた架空のタスク管理アプリ（TypeScript/Node）です。構成の全体を先に見ます。

```
agent-ops-task-app/
├── src/                          # アプリ本体（API + ドメインロジック）
├── tests/                        # Vitest のテスト
├── package.json                  # typecheck / test / lint スクリプト
├── CLAUDE.md                     # プロジェクトの最小限の前提
├── scripts/
│   └── weekly-metrics.sh         # 受理率の決定的な集計                ← 「品質評価」の章
├── .claude/
│   ├── settings.json             # permissions(deny) + Hooks 登録      ← 「ガードレール」の章
│   └── hooks/
│       └── block-outside-writes.sh  # プロジェクト外書き込みブロック   ← 「ガードレール」の章
└── .github/
    ├── agents.json               # planner / fixer / reviewer 定義     ← 「サブエージェント編成」の章
    ├── prompts/
    │   ├── nightly-triage.md     # 一次調査の指示                      ← 「ヘッドレス実行の基礎」の章
    │   ├── typefix.md            # 修正ジョブの契約書                  ← 「自律修正ループの設計」の章
    │   ├── triage.md             # Issue本文をデータ扱いする宣言       ← 「セキュリティ」の章
    │   ├── review.md             # レビューの手順                      ← 「品質評価」の章
    │   └── review-guidelines.md  # レビュー観点（チームの資産）        ← 「品質評価」の章
    ├── schemas/
    │   ├── triage-schema.json    # 一次調査の出力契約                  ← 「ヘッドレス実行の基礎」の章
    │   ├── typefix-schema.json   # fixed / skipped の報告契約          ← 「自律修正ループの設計」の章
    │   ├── issue-triage-schema.json # Issueトリアージの出力契約        ← 「セキュリティ」の章
    │   └── review-schema.json    # レビュー指摘の出力契約              ← 「品質評価」の章
    └── workflows/
        ├── nightly-triage.yml    # 夜間の一次調査（読み取り専用）      ← 「ヘッドレス実行の基礎」の章
        ├── nightly-typefix.yml   # 型エラーの自律修正ループ            ← 「自律修正ループの設計」「ガードレール」の章
        ├── issue-triage.yml      # Issueの安全なトリアージ             ← 「セキュリティ」の章
        ├── ai-review.yml         # PRの一次レビュー                    ← 「品質評価」の章
        └── weekly-metrics.yml    # 受理率・コストの週次集計            ← 「品質評価」「コスト管理」の章
```

このツリーには、本書の主張がひとつ埋まっています。 **エージェントの運用は、コードと同じ場所で、コードと同じようにバージョン管理する。** プロンプトも、権限も、観点も、スキーマも、全部リポジトリの中です。「あの人のプロンプト」ではなく `git log` が効く資産——これが、チームで運用する前提です。

## アプリ本体は、あえて平凡に

`src/` の中身は、タスクのCRUDと通知という、どこにでもあるAPIです。これは手抜きではなく設計です。題材が平凡であるほど、読者は自分のリポジトリとの対応を取りやすい。そして検出シグナルの3層—— `tsc --noEmit` （型）、 `vitest run` （テスト）、 `eslint .`（lint）——が `package.json` のスクリプトとして揃っていることが、唯一の必須要件です。「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で書いたとおり、 **検出器が揃っていることが自律修正ループの前提** であり、あなたのリポジトリでまず確認すべきものはこれです。

## 5本のワークフロー — 設計意図の総復習

各章では設計を示す最小例を扱い、リポジトリには統合版を置いています。ただし、本文の修正とリポジトリの更新は別管理で、時期によってずれます。2026-09-14時点の公開HEAD（コミット `de86518` ）の [nightly-typefix.yml](https://github.com/hampen2929/agent-ops-task-app/blob/de86518900a80515794de9b04c924956c6b66f95/.github/workflows/nightly-typefix.yml) を本文の掲載例と見比べたところ、前回の本文修正がまだ反映されておらず、代表的な差分が残っていました。

- Claude Code CLIのバージョンが固定されていない（本文は `2.1.263` に固定）
- 権限が `acceptEdits` と `--allowedTools` の組み合わせで、本文の `--tools` による提供ツールの限定と `dontAsk` になっていない
- checkoutに `persist-credentials: false` がなく、AIを動かすステップからGitの資格情報に手が届く
- 結果JSONの判定が `is_error` だけで、 `type` / `subtype` / `structured_output` の型まで見ていない
- 差分検査が作業ツリーの差分だけで、未追跡ファイルやステージ済みの変更を見ていない。コミットも `git add -A` で対象外のパスを拾い得る（本文は `git add -u -- src/` ）

したがって、公開リポジトリを「本と同等に整備済み」「そのまま本番で起動できる」ものとして扱わないでください。起動する前に、使うワークフローの各ステップを対応する章の掲載例と並べて照合し、足りない制御を補います。その順序は後の「動かすまでの手順」に置きました。ここでは「どの設計判断が、どこに効いているか」を1本ずつ確認します。右の列の原則は、本文で説明した順ではなく、そのワークフローを読むときに最初に探すべきものを挙げています。

| ワークフロー | 役割 | 効いている原則 |
| --- | --- | --- |
| nightly-triage | 失敗ログの夜間一次調査 | 読み取り専用から始める / `--bare` ・スキーマ出力 |
| nightly-typefix | 型エラーの検出→修正→検証→PR | 契約書プロンプト・二層防御・3つの出口 / 変更量上限 |
| issue-triage | 新規Issueへの見立てコメント | 信頼境界・データ扱い宣言・トークン隔離 |
| ai-review | PRへの観点ベース一次レビュー | 観点で縛る・一次受けと最終判定の分離 |
| weekly-metrics | 受理率の週次レポート | 決定的な集計。コスト集計は別途追加 |

このうち週次メトリクスだけは、これまで断片でしか見せていないので全文を載せます。「品質評価」の章の集計スクリプトをスケジュール実行し、結果をジョブのサマリーに出すだけの、意図的に地味なワークフローです。

```
name: Weekly Metrics
on:
  schedule:
    - cron: "0 0 * * 1" # 月曜 9:00 JST
  workflow_dispatch: {}

permissions:
  contents: read
  pull-requests: read

jobs:
  metrics:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v6
      - name: Collect
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          {
            echo "## AI運用 週次メトリクス"
            ./scripts/weekly-metrics.sh   # 受理率（「品質評価」の章）
            echo ""
            echo "コストは各ジョブのサマリーの cost_usd 行を集計（「コスト管理」の章）"
          } >> "$GITHUB_STEP_SUMMARY"
```

この例が自動計算するのは受理率だけです。コストの行は案内であり、ジョブ履歴から費用を集める実装ではありません。1マージあたりコストを自動化するには、失敗分も含む結果JSONの永続化と集計を追加します。

ここにAIは登場しません。 **メトリクスの集計は決定的なスクリプトの仕事** です。「機械で決定的にできることにAIを使わない」（「自律修正ループの設計」の章）は、運用の計器盤にこそ当てはまります。

## 4つの壁は、どこで守られているか

「 [なぜ「本番運用」は別物なのか](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/why-production-is-different) 」の章で挙げた4つの壁に、掲載例がどこまで対応し、何を追加する必要があるかをまとめます。真ん中の列が掲載例で扱っている制御、右の列が実行環境で追加するか、有効になっているかを確かめる制御です。

| 壁 | 掲載例で扱うもの | 本番導入時に追加・確認するもの |
| --- | --- | --- |
| **暴走** | ツール限定、時間・ターン・コスト上限、差分検査 | `--settings` によるフック有効化、設定の保護、Bash・MCPなど別経路の制限 |
| **品質** | 全体再実行、結果JSON検査、受理率の集計 | 手戻り・未処理PRの監視、必須チェックと人間のレビュー |
| **コスト** | 必要時のみAIを呼ぶ構造、ジョブ単位の推計 | 失敗分も含む費用の保存・週次集計、レビュー費などを含むROI |
| **監査** | PRラベル、コミットの出所表記、サマリー | 実行ログの外部保存、保持・アクセス制御、入力と対象コミットの相関 |

ファイルが置かれていることと、その制御が実行時に有効なことは別です。特に `--bare` は設定を自動で読み込みません。「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」章の設定を追加するときは、対象の起動コマンドへ `--settings .claude/settings.json` を渡し、拒否されるはずの操作が実際に拒否されるかを確かめます。denyルールについては、拒否されるはずの操作を含む小さなジョブを流し、結果JSONの `permission_denials` に記録が残るかを見るのが手軽です。

## 動かすまでの手順

リポジトリを自分の環境で動かす手順です。所要時間は認証・ブランチ保護・既存CIの状態によって変わるため、まず手動起動の確認までを一区切りにします。順序に意味があります。公開リポジトリのワークフローは前節のとおり本文と差があるので、 **Secretsを登録する前に** 、自動起動を止めた作業用コピーで内容を照合します。

1. **リポジトリをテンプレートとして自分のアカウントに作成** し、cloneする。この時点ではSecretsを登録しない
2. **自動起動を止める** 。テンプレートから作った直後でも、既定ブランチにあるワークフローは `schedule` や `issues` イベントで起動し得ます。照合が終わるまでは、リポジトリのActions設定で無効化するか、各ワークフローのトリガーを `workflow_dispatch` だけに書き換えたコミットを既定ブランチに入れておく
3. **本文の制御と照合し、補完する** 。使うワークフローを1本ずつ、対応する章の掲載例と並べて読みます。CLIバージョンの固定、 `--tools` と `dontAsk` による提供ツールの限定、 `persist-credentials: false` 、 `type` / `subtype` / `is_error` / `structured_output` を見る正常JSON判定、未追跡・ステージ済みを含む差分検査と `git add -u -- src/` 、 `--settings` によるフックの有効化。足りないものは補い、手元で最小の `claude --bare -p` と、壊した結果JSONを渡したときに失敗で止まることを確認する
4. **リポジトリ設定を整える** 。 `ai-generated` ラベルの作成、mainのブランチ保護（必須レビュー1名以上）、Actionsの権限設定。 `GITHUB_TOKEN` でPRを作る場合は「Allow GitHub Actions to create and approve pull requests」を有効にする（この設定は作成と承認をまとめて許可するので、人間の承認はブランチ保護で必須にする）
5. **認証を設定する** 。個人ならリポジトリのSecretsに `ANTHROPIC_API_KEY` を登録。組織ならOIDC連携か `apiKeyHelper` （「企業環境への導入」の章）を最初から検討する
6. **読み取り専用ジョブだけを手動で動かす** 。 `nightly-triage.yml` は `workflow_dispatch` で手動実行する。 `issue-triage.yml` はソースに対して読み取り専用ですが、Issueへのコメント投稿という外部への書き込みを含みます。手動起動イベントは定義していないので、許可対象のアカウントでテスト用Issueを作って発火させ、投稿されたコメントの内容とコストを確認する。問題がなければ、手順2で外した `schedule` と `issues` トリガーを戻す
7. **1〜2週間、計器を見る** 。 `weekly-metrics.yml` の数字と各ジョブのコストが安定していることを確認する
8. **書き込みジョブを解禁する** 。 `nightly-typefix.yml` を手動実行し、意図的に直せない型エラーを置いた状態で、PRが出ずに失敗として止まりサマリーに理由が残ることを先に確かめる。それからスケジュール化し、最初の数本のPRは必ず精読する

手順の6〜8が、本書全体で繰り返してきた **信頼の階段** です。テンプレートを手に入れても、階段は飛ばさない。読み取り専用の観察期間に得られるコスト実測と出力の傾向が、書き込みを任せる判断の根拠になります（そしてこの手順自体が、「 [企業環境への導入](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/enterprise) 」の章のPoC→パイロットの個人版です）。

この8手順は、本書が題材のアプリで追ってきた判断の順序そのものでもあります。手順3と6で実行結果の判定を確かめ、手順8で修正と、検証に落ちたときの停止を確かめ、出てきたPRを人間がレビューする。手順7と週次の計器が、任せる範囲を広げるか止めるかの運用判断を支えます。なお、本書の推敲ではこの手順をGitHub Actionsで通しで実走した確認はしていません。ローカルでの構文検査と判定処理の検証が根拠です。

## 自分のプロジェクトへの適用チェックリスト

最後に、このリファレンス実装をあなたの本物のリポジトリに移植するときのチェックリストを置きます。各項目は該当章への索引にもなっています。第1部は「 [ヘッドレス実行の基礎](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/headless-basics) 」から「 [サブエージェント編成](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/subagents) 」、第2部は「ガードレール」と「 [セキュリティ](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/security) 」、第3部は「 [品質評価](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/quality-evals) 」から「企業環境への導入」に対応します。

**第1部 土台**

- 無人化するタスクは3条件（可逆・機械判定可能・文脈が閉じる）を満たすか。最初は読み取り専用か
- 検出シグナル（型・テスト・lint）がスクリプト1発で走る状態か
- `claude --bare -p` + JSON + スキーマの最小ジョブが手元で動くか
- 終了コードと `is_error` の両方をチェックしているか
- 修正プロンプトに、作業範囲・skipの退路・禁止事項・出力契約が明文化されているか
- 検証は「対象だけ」でなく「全体再実行」か。合否を決めるのはAIの自己申告ではなくCIか
- ジョブが大きくなったときの分割方針（Plan→Execute・役割分担）を知っているか

**第2部 守り**

- 出口はPRのみか。mainへ直接書く経路が存在しないか
- シークレット・SSH設定などへのdenyルールがコミットされているか
- Edit / Writeのフックに加え、BashやMCPを含む別経路をツール制限・サンドボックスで塞いでいるか
- 時間・ターン・コスト・変更量の上限が全ジョブに掛かっているか
- フォークPR・Issue本文など「他人が書ける入力」を、書き込み権限を持つジョブに直結させていないか
- エージェントのステップの環境変数に、不要なシークレットが存在しないか
- MCPを使わないジョブは `--bare` で遮断しているか

**第3部 運用**

- 受理率・手戻り率・1マージあたりコストを、週次で見る仕組みがあるか
- モデル・プロンプトを変えるとき、代表ジョブで回帰検証してから本番に戻しているか
- 実行ログ（何を読み・何を実行し・いくら使ったか）が、ジョブの外に保存されているか
- AI生成の変更が、ラベルとコミット表記で機械的に識別できるか
- 「ここまで悪化したら止める」撤退基準を先に決めてあるか

最初から全項目を満たす必要はありませんが、後回しにしてよいのは **まだ使っていない機能の項目** だけです。サブエージェントを使わないうちは分割方針の項目を、MCPを使わないうちはMCPの項目を空けておいて構いません。一方、実行するジョブに関わる項目——認証、提供ツールの範囲、上限、失敗時の停止、出口がPRであること、人間のレビュー——は、そのジョブを動かす前に満たします。本書の順序——読み取り専用の1本から始めて、計器を見ながら1段ずつ——は、満たす項目を段階ごとに増やしていく順序でもあります。

## おわりに — 「たまに使う便利ツール」の先へ

本書の冒頭で、こう問いました。 **あなたが寝ている間も、Claude Codeは働いていますか。**

いまのあなたは、この問いに設計で答えられるはずです。無人にすることの本当の意味。CIに載る部品の作り方。修正ループの設計。スケールする編成。事故と攻撃への守り。品質とコストの計器。組織に載せる道筋。そして、全部をつなげた1つのリポジトリ。

最初の一歩は、驚くほど小さくできます。あなたのリポジトリに、読み取り専用の夜間ジョブを1本置く。それだけです。明日の朝、最初のサマリーが届いたとき、「たまに使う便利ツール」が「毎晩黙って働くチームメンバー」に変わる道の、最初の一段を登ったことになります。

ここで作ったシステムには、続きがあります。1体のエージェントの本番運用の先にあるのは、複数のエージェントを **チームとして設計し、育てる** 世界です。その話は、次の本で。

ここまで読んでいただき、ありがとうございました。あなたの最初の夜間ジョブが、静かに回り続けますように。
