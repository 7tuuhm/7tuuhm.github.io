## 企業環境への導入 — 稟議・監査・段階展開

[

はんぺん

2026.09.14に更新

](https://zenn.dev/hampen2929)

ここまでの8章で、無人で動き・守られ・測られるシステムができました。個人やチームのリポジトリでなら、もう回せます。

この章は、それを **会社に置く** 話です。技術は増えません。増えるのは、稟議・監査・調達・展開という、技術者が普段あまり触らない関門です。そして「 [なぜ「本番運用」は別物なのか](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/why-production-is-different) 」の章で「監査の壁」と呼んだもの——「このコミットは誰の意思か」「セキュリティチームに何ができて何ができないかを説明できるか」——が、ここで本丸になります。

筆者は本業で規制の強い業界のシステム開発に関わっています。この種の環境では、どんなに良いシステムでも「説明できなければ導入できない」。この章は、作ったシステムを **説明可能な形で組織に載せる** ための地図です。導入責任者でない人にも、自分のジョブがレビューでどこを問われるかを先に知る材料になります。

## 実行環境と認証 — どこでモデルを呼ぶか

組織導入の最初の分岐は、技術構成ではなく「どこでモデルを呼ぶか」です。これは調達・ネットワーク・データ取り扱いのポリシーで決まります。選択肢は3つで、右の列の「向く組織」に自分の組織が当てはまるかで読んでください。

| 経路 | 概要 | 向く組織 |
| --- | --- | --- |
| Claude API 直接 | APIキー/サブスクで直接呼ぶ | 制約の緩いチーム |
| クラウドプロバイダ経由 | Amazon Bedrock / Google Cloud / Microsoft Foundry 上で呼ぶ | 既にそのクラウドを契約・データを外に出せない組織 |
| セルフホストゲートウェイ | 社内IdPでSSOし、推論を指定先へ流す | SSO統合・一元監査が要る組織 |

規制の強い環境で効いてくるのが2番目です。既に契約しているクラウド経由でモデルを呼べば、既存の調達・統制を使える場合があります。ただし、 **リージョン・保存・ログ・通信経路の条件はサービスごとに確認が必要** です。「新しいベンダーにデータを出す」稟議ではなく「既存クラウドの一機能を使う」稟議になり、通しやすさが大きく変わります。プライベートネットワーク構成も、そのクラウドのVPC設計にそのまま乗ります。

## CIの認証設計

「 [ヘッドレス実行の基礎](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/headless-basics) 」の章では、 `--bare` 付きCLI例にAPIキーを使いました。組織展開では、資格情報の取得元と有効期限まで設計します。

まず注記です。本書はCIで `--bare` を推してきましたが、 **`--bare` は `CLAUDE_CODE_OAUTH_TOKEN` を読みません** 。OAuthトークンを使う個人向けの構成は、 `--bare` と組み合わせると認証が通らない。 `--bare` のCIでは `ANTHROPIC_API_KEY` か、次に述べる `apiKeyHelper` を使います。

そして、組織で本命になるのが **静的なキーを置かない認証** です。「 [セキュリティ](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/security) 」の章で「シークレットは届かせない」「短命な資格情報を使う」と書いた、その実装がここです。

- **クラウドプロバイダのOIDC連携**: たとえばBedrockやGoogle Cloud経由では、CIのIDをクラウド側の短命な資格情報に交換する構成を取れます。Claude API直接の認証とは別の経路です。利用するプロバイダで信頼ポリシーと有効期限を設定します
- **`apiKeyHelper`**: APIキーを取得して返すスクリプトを指定します。 `--bare` でも使えますが、helper自体がキーを短命化するわけではありません。保管・発行・ローテーションは取得元で設計します

「静的なAPIキーをSecretsに置く」のは、動きますが、組織のセキュリティレビューでは最初に指摘される構成です。最初からOIDC連携で設計しておくと、後述のセキュリティレビューが一段軽くなります。

## 統制を組織で固定する — managed settings

個人利用では、権限設定（「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」の章）は各自が `.claude/settings.json` に書くものでした。組織展開では、「 **守ってほしいことを、個人が外せない形で固定する** 」必要が出てきます。

Claude Codeには、組織が設定を強制する仕組み（managed settings）があります。デバイス管理ツールで配布し、個人のローカル設定より優先させることで、次のような統制を全社に効かせられます。

- **ログイン先の制限**: `forceLoginMethod` / `forceLoginOrgUUID` で、会社の組織アカウント以外でのログインを起動時に弾く。私物アカウントでの利用や、シャドーITを防ぐ
- **権限の固定**: 「ガードレール」の章のdenyルール（シークレット・危険操作の禁止）を、個人が緩められない層で強制する
- **監査の強制**: 後述のテレメトリ設定を、オプトアウトできない形で配る

「ガードレール」の章で「ルールはモデルではなくハーネスに書く」と書きました。組織展開では、そのハーネスの設定自体を **個人の手の届かない層に置く** 。ガードレールを、一人ひとりの良心ではなく、組織の設定として敷くわけです。

## 監査ログ — 「誰が何をしたか」を残す

「なぜ「本番運用」は別物なのか」の章で挙げた監査の壁への、最終的な答えがここです。そして「セキュリティ」の章で「うまくいった攻撃は症状を出さない、だから記録で追う」と書いた、その記録基盤の作り方です。

Claude CodeはOpenTelemetryでメトリクスとイベントログを外部に出せます。有効化すると、監査に必要な情報が構造化されて手に入ります。「誰が・何を・どうなった」の順に、監査で問われる項目と対応させると次のようになります。

| 取れるもの | 例 | 監査での用途 |
| --- | --- | --- |
| 誰が | `user.email` / `organization.id` | 主体の特定 |
| 何を | `tool_decision` （ツール名・accept/reject・決定元） | ツール呼び出しを許可・拒否した判断の記録 |
| 結果 | `tool_result` （成否・エラー種別） | 実際に実行された操作とその結果 |
| コード変更 | `lines_of_code.count` | 変更規模の監視 |
| コスト | `cost.usage` / `token.usage` | 支出の追跡（「コスト管理」の章） |
| 拒否された操作 | `decision = reject` | 攻撃・逸脱の試みの可視化 |

`tool_decision` と `tool_result` は別のイベントとして読みます。前者は許可判断の記録なので、許可が出たことを実行に成功したことと同一視しないでください。何が実際に起きたかは後者で確認します。 `prompt.id` や `tool_use_id` といった相関IDで、「あるジョブが、何を読み、何を実行し、いくら使い、どのコミットを生んだか」を1本の線として追えます。より詳細な監査が要る環境では、プロンプト本文やツールの入出力まで記録するオプションもあります（ただし、その内容自体が機密になり得るので、保存先の保護とセットで設計します）。

設計の要点は3つです。

1. **改竄できない場所に集約する** 。ジョブが吐くログを、そのジョブ自身が消せる場所に置いては監査になりません。書き込み専用の外部集約先へ流します
2. **保持期間を決める** 。監査要件（何年遡れる必要があるか）から逆算します
3. **最初から入れる** 。「なぜ「本番運用」は別物なのか」の章で「ログが残る構造は後付けできない」と書いたとおり、パイロットの初日からテレメトリを有効にしておきます

設定しただけで監査が完成するわけではありません。代表ジョブのイベントを集約先で検索し、実際のコミットと相関できることを確認して、初めて「追える」と言えます。

## 承認フロー — 人間の意思を記録に残す

技術的な監査ログと対になるのが、 **承認** という人間の意思決定の記録です。本書は一貫して「出口はPR、最後は人間のマージ」と設計してきました。組織展開では、この最後のマージを **統制された承認フロー** にします。

- **ブランチ保護**: mainへの直接pushを禁止し、PRのマージに必須の承認者数を設定する
- **CODEOWNERS**: 変更された領域のオーナーの承認を必須にする。AIが触った領域の責任者が、必ず目を通す構造
- **AI生成PRの識別**: 「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で付けた `ai-generated` ラベルを使い、追加のチェックでAI生成PRを識別する。ラベルだけで必須承認数が自動的に変わるわけではないため、上乗せする場合はルールや検証処理を別に実装する
- **作成と承認の扱い**: GitHubの「Allow GitHub Actions to create and approve pull requests」は作成と承認をまとめて許可する設定です。PR作成のために有効化しても、人間の承認が必須になるとは限りません。AIには投稿用トークンを渡さず、信頼済みの公開ステップとブランチ保護・CODEOWNERSで承認経路を管理します

こうすると、すべての本番変更に「誰がマージを承認したか」という人間の意思が記録として残ります。「なぜ「本番運用」は別物なのか」の章の「このコミットは誰の意思か」に、コミットの出所（「セキュリティ」の章）と承認者の両方で答えられる状態です。

## セキュリティレビューの通し方

導入の関門として最大のものが、セキュリティチームのレビューです。ここを通すコツは、 **「セキュリティ」の章の脅威モデルを、そのまま説明の道具として使う** ことです。

セキュリティレビュアーが本当に知りたいのは、たった2つです。 **このエージェントは何ができるのか。何ができないのか。** 漠然と「AIが怖い」のではなく、権限の境界が示せないことが怖いのです。本書の設計は、この2つに具体的な答えを持っています。問われ方や順序は組織ごとに違うので、次の表は回答と、その根拠になる設定やログの置き場所を対応づける索引として使ってください。

| 問われること | 本書のどこで答えるか |
| --- | --- |
| 何ができるのか | `--tools` ・ `--allowedTools` ・permissions（「ヘッドレス実行の基礎」「ガードレール」の章）＝許可された操作の明示リスト |
| 何ができないのか | denyルール・サンドボックス（「ガードレール」の章）＝OSレベルで塞いだ境界 |
| 操られたらどうなるか | 脅威モデルと多層防御（「セキュリティ」の章）＝騙されても被害が出ない構造 |
| 何をしたか追えるか | 監査ログ（本章）＝全操作の記録 |
| 漏れたら | シークレット最小化・短命資格情報（「セキュリティ」の章・本章） |

つまり、「ヘッドレス実行の基礎」の章から積み上げてきた設計そのものが、セキュリティレビューの回答書になります。「権限はこの設定ファイルで宣言的に定義され、これはOSが強制し、全操作はこのログに残る」と、設定ファイルとログのスキーマを見せながら説明できる。これは「気をつけて使います」という精神論とは、審査の通りやすさが根本的に違います。

Anthropicが提供するコンプライアンス資料（SOC 2 Type 2 レポート、ISO 27001 認証など）も、ベンダー審査の材料として使えます。データの取り扱いについては、先述のクラウドプロバイダ経由構成が「既存契約の統制の内側で使う」という回答の候補になります。ただし、クラウド経由というだけで域内保持や統制が保証されるわけではないので、リージョン・保存・ログの条件をそのサービスの仕様で確認してから答えます。

## 段階展開 — PoC → パイロット → 全社

最後は、組織に広げる順序です。本書が全編で繰り返してきた原則—— **信頼は一段ずつ積む** ——が、ここで組織のプロセスになります。

図の実線が前進、点線が撤退です。PoCからパイロットへ、パイロットから複数チームへの矢印には判断の菱形が挟まっていて、どちらからも撤退の点線が出ています。PoCからパイロットへの矢印に「受理率」とありますが、PoCは読み取り専用なので修正PRは出ず、修正PRの受理率はまだ測れません。PoCで確かめるのは、一次調査や一次レビューの内容が妥当か、コストが想定内か、逸脱がないかです。修正PRの受理率と手戻り率は、書き込みジョブを動かすパイロットで初めて測れます。各段階の中身と、次に進む判断基準はこうなります。

- **PoC**: 1つのリポジトリで、読み取り専用ジョブ（一次調査・PRレビュー）だけを回す。「なぜ「本番運用」は別物なのか」の章で「読み取り専用から始める」と書いた、あの原則の組織版。目的は性能の証明ではなく、 **運用の勘所とコスト実測を掴む** こと。判断材料は、調査やレビュー結果の妥当性を人間が確かめた結果、コストの実測、逸脱の有無
- **パイロット**: 1チームで、書き込みを伴う自律修正ジョブに広げる。ここで初めて「自律修正ループの設計」の章のループが本番投入されます。判断材料は「 [品質評価](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/quality-evals) 」「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」両章のメトリクス——受理率、手戻り率、1マージあたりコスト、そして逸脱の有無
- **複数チーム展開**: パイロットの構成（ワークフロー・設定・プロンプト）をテンプレート化して配る。ここでmanaged settingsによる統制が効いてきます
- **全社標準化**: 監査・承認・統制を組織の標準として固定する

そして、忘れてはいけないのが **撤退の基準** です。各段階で「これを満たさなければ次に進まない、それどころか止める」という線を、始める前に決めておきます。受理率が想定を大きく下回る、手戻りが多い、コストが見合わない——サンクコストで突き進まず、設計に戻るか撤退する判断を、メトリクスに基づいて下せるようにしておきます。段階展開は「広げる計画」であると同時に「止められる構造」でもあります。

## まとめ

- 組織導入で増えるのは技術ではなく、稟議・監査・調達・展開の関門。「なぜ「本番運用」は別物なのか」の章の「監査の壁」がここで本丸になる
- 実行環境は **データポリシーで決まる** 。規制環境では **クラウドプロバイダ経由** （既存契約の統制を使いやすい。域内保持などの条件はサービスごとに確認）が通しやすい。CIの `--bare` は OAuthトークンを読まない—— **APIキーか、OIDC連携・ `apiKeyHelper` による短命資格情報** で
- 統制は **managed settings** で個人が外せない層に固定する。ログイン制限・権限・監査を組織設定として敷く
- 監査ログは **OpenTelemetry** で「誰が・何を・結果・コスト・拒否」を構造化して残す。改竄できない場所へ、最初から。「セキュリティ」の章の「攻撃は記録で追う」の実装
- 承認フローはブランチ保護・CODEOWNERS・AI生成PRへの上乗せ。 **すべての本番変更に人間の承認を記録として残す**
- セキュリティレビューは、 **「セキュリティ」の章の脅威モデルを説明の道具に** 。「何ができて・何ができないか」を設定ファイルとログで示せるのが本書の設計の強み
- 展開は **PoC→パイロット→複数チーム→全社** 。信頼を一段ずつ積む組織版。各段に **撤退基準** を先に決め、止められる構造にする

第3部はここまでです。無人で動くシステムを、守り、測り、組織に載せるところまで来ました。残すは実践——最終章「 [リファレンス実装](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/reference-implementation) 」で、本書の全部品を1つのリポジトリに組み上げ、動くリファレンス実装として通しで解説します。ここまで章ごとに示してきた断片が、1つのつながったシステムになります。
