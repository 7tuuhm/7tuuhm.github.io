## 品質評価 — 「動いた」を「信頼できる」にする

[

はんぺん

2026.09.14に更新

](https://zenn.dev/hampen2929)

第3部に入ります。ここまでで、ループは回り（第1部）、事故と攻撃から守られています（第2部）。個々のジョブは、検証ゲートを通ったものだけがPRになる——「 [自律修正ループの設計](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/autonomous-fix-loop) 」の章で作ったこの仕組みは、「1本のジョブが壊れていないか」をちゃんと見ています。

しかし、毎晩・複数のリポジトリでループが回り始めると、検証ゲートだけでは答えられない問いが出てきます。

**このAI運用は、任せ続けてよい水準で回っているのか。**

個別のPRが緑なのは分かる。では、AIが出したPRの何割が実際にマージされている？　マージ後に手戻りは起きていない？　先月モデルを更新してから、品質は上がった？　下がった？——これらは1本のジョブの中には答えがありません。 **システム全体を、時間をまたいで** 見る必要があります。

この章は、個別ジョブの検証ゲートから、運用全体の品質評価へと視点を上げます。「動いた」を「信頼できる」に変える話です。

## 「動いた」と「信頼できる」の間

「 [なぜ「本番運用」は別物なのか](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/why-production-is-different) 」の章で「壁2: 品質」として触れた問題を、ここで正面から扱います。 **テストが通ったことは、意図どおりであることを意味しません。**

「自律修正ループの設計」の章の検証ゲートは「型チェック・テスト・lintが、修正前より悪化していないか」を見ていました。これは必要な検査ですが、通り抜けるものがあります。

- **動くが、設計方針に反する実装** 。テストは通るが、既存のパターンを無視した書き方
- **報告と差分の食い違い** 。「型エラーを直した」と報告しつつ、実際は別の箇所も触っている
- **テストの穴を通り抜けた欠陥** 。そもそもテストがカバーしていない挙動の変化

つまり「機械検証を通った」と「信頼できる」の間には、まだ隙間があります。この隙間を埋めるのが品質評価で、道具は2つです。 **合格条件の設計** （何をゲートにするか）と **メトリクス** （結果を測って改善に回すか）。順に見ます。

## 合格条件の設計 — 何を機械に、何を人間に残すか

品質保証の出発点は、「合格」の定義です。そして最も重要な設計判断は、 **機械で判定できることと、人間の判断が要ることを、はっきり分ける** ことです。

| 判定の種類 | 例 | 誰が担うか |
| --- | --- | --- |
| 機械判定できる | テスト成否・ビルド・型・lint・スキーマ適合・差分範囲 | 検証ゲート（自動） |
| 機械判定できない | 設計の妥当性・仕様の解釈・変更の必要性そのもの | 人間のレビュー |

この切り分けが、本書の一貫した構造—— **検証は機械が先、人間が後** （「なぜ「本番運用」は別物なのか」の章のアーキテクチャ原則）——の品質面での定義です。機械判定できるものは全部ゲートに寄せ、人間を「機械に判定できないところ」に集中させる。

ここで陥りやすい罠が2つあります。

**罠1: 機械判定できるものを人間に残す。** 「一応、目視でも確認しよう」で型チェックやテストを人間が手元で再演するのは、認知の無駄です。機械が決定的に判定できることは機械に任せ切る。人間の目は有限の資源で、それを型エラーの再確認に使うと、設計レビューに回す分が減ります。ただし、任せ切るのは判定の再演であって、判定の存在確認ではありません。必要なチェックがそのPRの最新コミットに対して実行され、結果が合格だったかは、人間がPR上で確かめます。

**罠2: 機械判定できないものを機械に押し付ける。** 「このコードは良い設計か」をAIレビュアーにスコア判定させて自動マージ、はやってはいけません。「 [サブエージェント編成](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/subagents) 」の章で書いたとおり、AIレビュアーは一次受けであって最終判定者ではない。設計の妥当性という機械判定できない領域の合否は、人間のマージに残します。

「自律修正ループの設計」の章の型エラーPRに当てはめると、こうなります。型チェック・テスト・lintの実行は、PRを開く前にワークフローが済ませています。人間がまず確かめるのは、そのチェックがPRの最新コミットに対して走り、合格しているかです。それが確認できたら、同じチェックを手元で繰り返す必要はありません。その上で人間が判断するのは、差分が報告どおりの意味を持つか、直し方が既存のパターンに沿っているか、skipの理由に納得できるか、そもそもこの修正が必要だったか、そして既存のテストがこの変更を検証できていたかです。この線引きを守るほど、レビューの時間を設計の判断に回せます。

合格条件を厚くする王道は、実は評価の技術ではなく **テストを増やすこと** です。AIが自律修正するリポジトリでは、テストの網の目の細かさが、そのまま検証ゲートの精度になります。「テストが薄いリポジトリほど、AIの自律運用は危険」——「自律修正ループの設計」の章で依存更新を「テストの厚み次第」と条件付きにしたのは、この理由です。逆に言えば、AI運用の品質を上げる最も確実な投資は、テストカバレッジを上げることだったりします。

## メトリクス — システムの健康を数字で見る

合格条件が「1本のジョブ」の品質だとすれば、メトリクスは「運用全体」の品質です。「 [ヘッドレス実行の基礎](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/headless-basics) 」の章で、個別ジョブから `is_error` やコストが取れることを見ました。それらを **集計して時系列で見る** と、システムの健康状態が見えてきます。

無人運用でまず見るべきメトリクスは3つです。定義と一緒に、その数字が答える問いを並べます。

| メトリクス | 定義 | 何が分かるか |
| --- | --- | --- |
| **受理率** | AIが出したPRのうち、マージされた割合 | 成果物が「使える」水準にあるか |
| **手戻り率** | マージ後に修正・revertされた割合 | 「見かけの合格」がすり抜けていないか |
| **修正リードタイム** | ジョブ起動からマージまでの時間 | 人間のレビュー負荷が回っているか |

この3つは、単独ではなく **組み合わせで** 読みます。

- 受理率が高く、手戻り率が低い → 健康。任せる範囲を広げる判断材料になる
- 受理率が低い → AIの出力が使えていない。プロンプトかタスク選定を見直す
- **受理率が高いのに手戻り率も高い → 危険信号** 。これは「レビューがザルで、悪いPRも通っている」状態を示します。「自律修正ループの設計」の章で「レビュー形骸化の入口」と呼んだ現象が、数字に出ている形です

3つめの組み合わせが、品質評価の核心です。受理率だけを見ていると「うまくいっている」と誤認します。受理率は「人間がOKした割合」であって「実際に正しかった割合」ではないからです。手戻り率という「後から分かる真実」と突き合わせて初めて、運用の実態が見えます。

![受理率×手戻り率の4象限 — 右上「受理率が高いのに手戻り率も高い」がレビュー形骸化の危険信号](https://static.zenn.studio/user-upload/deployed-images/4ca931f03a8bd2406f755070.jpg?sha=7e9c68102df01e3c1580aac5e15f46b56231b8b5)

架空の状況で読み方を確かめます。タスク管理アプリの夜間型修正ジョブを1か月回し、出たPRのほとんどがマージされたとします。受理率だけ見れば順調です。ところが、マージ後に同じファイルを人が直し直したPRが目立つなら、図の右上に入っています。このとき最初に疑うのはAIの出力ではなく、レビューです。差分を読まずに承認していないか、テストがその変更を検証できていたか。逆に、受理率が低くても手戻りがほぼ無いなら、人間のレビューは機能していて、直すべきはタスクの選び方かプロンプトです。同じ「品質が悪い」でも、2つの数字の組み合わせで手を入れる場所が変わります。

## 受理率を測る — 最小の実装

メトリクスは、凝った基盤がなくても始められます。「自律修正ループの設計」の章で、AIが出すPRに `ai-generated` ラベルを付けていました。これを起点に、 `gh` CLIで集計できます。スクリプトの要点は2つで、 `--paginate` で全件を取ることと、分母を「期間内に採否が決まったPR」に限っていることです。

```
#!/usr/bin/env bash
set -euo pipefail
# GNU date (Linux/CI) と BSD date (macOS) の両対応で過去7日
since="${1:-$(date -d '7 days ago' +%Y-%m-%d 2>/dev/null || date -v-7d +%Y-%m-%d)}"

# gh pr listの既定件数で切らず、全ページを取得する。
repo=$(gh repo view --json nameWithOwner --jq '.nameWithOwner')
counts=$(gh api --paginate "repos/$repo/pulls?state=closed&per_page=100" |
  jq -s --arg since "$since" '
    add | map(select(any(.labels[]?; .name == "ai-generated"))) |
    {
      merged: (map(select(.merged_at != null and .merged_at >= $since)) | length),
      closed: (map(select(.merged_at == null and .closed_at >= $since)) | length)
    }')
merged=$(printf '%s' "$counts" | jq -r '.merged')
closed=$(printf '%s' "$counts" | jq -r '.closed')
total=$((merged + closed))

if [ "$total" -eq 0 ]; then echo "対象PRなし"; exit 0; fi
rate=$(awk "BEGIN{printf \"%.0f\", $merged/$total*100}")
echo "受理率(過去7日): ${rate}% (${merged}/${total} マージ)"
```

これは期間内に採否が決まったPRの受理率です。レビュー中のPRは分母に含みません。大量に未処理PRが溜まっていても値は高く見えるため、未処理件数と滞留日数を併記します。

これを週次のワークフローで走らせ、結果をどこか（Slack・ダッシュボード・GitHub Issue）に出すだけで、「AI運用の受理率」という数字が毎週手元に来ます。凝るのは、数字を見る習慣がついてからで十分です。

手戻り率はもう少し工夫が要ります。「マージ後、一定期間内にそのファイルが再修正されたか」「revertコミットがそのPRを指しているか」で近似します。完全な計測は難しいので、まずはrevert検出だけでも始める価値があります。

## コスト当たりの品質

もうひとつ、無人運用で特に効くメトリクスがあります。 **1マージあたりのコスト** です。「ヘッドレス実行の基礎」の章で各ジョブの `total_cost_usd` が取れました。これを受理されたPR数で割ると、「使える成果物1本にいくらかかっているか」が出ます。

受理されなかったジョブのコストも分子に含めるのがポイントです。10本のジョブを走らせて3本がマージされたなら、コストは10本分、成果は3本。この「1マージあたりコスト」こそがROIの実数で、詳しくは次の「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」の章で扱います。品質とコストは別々の話ではなく、 `コスト当たり品質` という1つの指標で結ばれます。

## 回帰検証 — 変化に品質を追随させる

無人運用の品質は、放っておくと **勝手に変わります** 。あなたが何もしなくても、だいたい次の3つが動くからです。

- **モデルの更新** 。新しいモデルに切り替えたら、同じプロンプトの挙動が変わる
- **プロンプト・ルールの変更** 。CLAUDE.mdやプロンプトを改善したつもりが、別のタスクを劣化させる
- **リポジトリの変化** 。コードベースが育つと、同じジョブでも難易度が変わる

対話利用なら、変化に気づいたその場で調整できます。無人運用では、変化は静かに起きて、メトリクスが下がって初めて気づく——しかもメトリクスは遅行指標なので、気づいた頃には何日分も低品質な成果物が積み上がっています。

これに対する備えが **回帰検証** です。考え方はソフトウェアのテストと同じで、「既知の入力に対して、期待される挙動が保たれているか」を、変更の前後で確認します。

無人運用での最小の回帰検証は、 **代表的なジョブを固定した題材で流す** ことです。

- 既知のバグを1つ含んだ、固定のコード断片を用意する（サンプルアプリの中に「回帰検証用の題材」を置いておく）
- モデル更新やプロンプト変更のたびに、そのジョブを流す
- 「期待どおり検出・修正できたか」「禁止事項を守ったか」「コストは想定内か」を確認する

これは「ゴールデンセット」と呼ばれる評価手法の、ごく小さな入り口です。本格的には、多様なケースを集めたデータセットを作り、版管理し、判定を自動化していく——その体系は評価を主題とする続刊の中心テーマなので、本書では「モデルやプロンプトを変えたら、代表ジョブを1本流してから本番に戻す」という習慣の導入までに留めます。この習慣があるだけで、「モデル更新したら急にPRの質が落ちた」という事故の多くは、本番に出る前に捕まえられます。

## 評価を設計に還元する — ループを閉じる

メトリクスと回帰検証は、測るだけでは意味がありません。 **測った結果を設計変更に還元し、次の品質を上げる** ——このループが閉じて初めて、評価は機能します。

数字が悪化したとき、どこに手を入れるか。症状ごとに切り分けます。左の症状から、真ん中の「疑う場所」を経て、右の打ち手と該当章へ戻る索引として使ってください。

| 症状 | 疑う場所 | 打ち手 |
| --- | --- | --- |
| 受理率が低い | タスク選定・プロンプト | 対象を絞る / プロンプトの契約を明確化（「自律修正ループの設計」の章） |
| 手戻り率が高い | 検証ゲート・レビュー | ゲートを厚く（テスト追加）/ 人間レビューの役割再定義 |
| 特定タスクだけ質が低い | そのタスクの適性 | 無人化の3条件（「なぜ「本番運用」は別物なのか」の章）で再評価・対象から外す |
| コスト当たり品質が悪化 | 編成・モデル選択 | Plan→Execute分離（「サブエージェント編成」の章）/ モデル使い分け |
| 逸脱・禁止事項違反 | ガードレール | 宣言・Hooksで強制に昇格（「 [ガードレール](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/guardrails) 」の章） |

この表が示すのは、 **品質評価は本書の全部の章に還元先を持つ** ということです。評価は独立した工程ではなく、ここまでの章で作った各部品への **フィードバック機構** です。

そして還元先は、コードだけではありません。振り返りで得た学び——「このパターンの修正は失敗しやすい」「この観点は人間が見るべき」——は、CLAUDE.mdやレビュー観点、ガードレールのルールに書き戻します。障害の再発防止策として「ルールを1行足す」が選択肢に入る状態を、品質評価が駆動します。人が抜けても、失敗から得た学びはリポジトリに残る。これは無人運用の話であると同時に、チームの資産形成の話でもあります。

## 品質評価を組み込んだ運用の姿

第1部で作った左半分（ジョブ→ゲート→PR→マージ）に、この章は右半分（メトリクス→評価→還元）を足しました。左半分は「1回を正しく回す」仕組み、右半分は「回し続けて良くする」仕組みです。図で見てほしいのは、右半分からジョブへ戻る2本の点線です。品質低下からの還元と、回帰検証を通った変更の反映——この2本があって初めて、評価が設計に戻ります。無人運用が「立ち上げて終わり」ではなく「育てるもの」になるのは、この右半分があるからです。

## まとめ

- 個別ジョブの検証ゲート（「自律修正ループの設計」の章）は「1本が壊れていないか」を見る。品質評価は **運用全体を時系列で** 見て、「任せ続けてよい水準か」に答える
- 「動いた」と「信頼できる」の間には隙間がある。合格条件は **機械判定できるものと人間の判断が要るものを分ける** 。機械判定は機械に寄せ切り、人間はチェックが対象コミットに対して実行済みかの確認と、差分の意味・設計の判断に集中する
- メトリクスの核は **受理率・手戻り率・修正リードタイム** を組み合わせて読むこと。特に「受理率が高いのに手戻り率も高い」はレビュー形骸化の危険信号。まずは `gh` CLIでの受理率集計から始められる
- 品質は放っておくと変わる（モデル更新・プロンプト変更・リポジトリの成長）。 **回帰検証** ——代表ジョブを固定題材で流す——で、変化を本番前に捕まえる
- 測るだけでは無意味。 **評価を設計に還元する** ループを閉じる。還元先は本書の全章（プロンプト・ゲート・ガードレール・タスク選定・モデル選択）とCLAUDE.md

次の「 [コスト管理](https://zenn.dev/hampen2929/books/claude-code-production-guide/viewer/cost) 」の章では、この章で触れた「1マージあたりコスト」を軸に、トークンコストの構造・計測・最適化を扱い、AI運用を「いくらで、どれだけの価値を生んでいるか」で語れるようにします。受理率という分母を持ち越すことで、コストの話が「安くする」だけでなく「見合っているか」の判断になります。
